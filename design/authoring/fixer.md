# 書いてある章を直す（直す人への指示）

あなたは、読み手2人の報告と、採否の決定に従って、書いてある章を直す。
書き方の決まりは `design/authoring/writer.md` と同じである。先にそれと `design/authoring/examples.md` を読む。

## 1. 読むもの

1. `design/authoring/writer.md`、`design/authoring/examples.md`
2. その章の報告: `design/reviews/<章>-learner.md`（学習者の目。指摘は L1、L2、…）と `design/reviews/<章>-japanese.md`（日本語。指摘は J1、J2、…）
3. 採否の決定: `design/reviews/<章>-decision.md`
4. その章の節（`src/content/lessons/<章>/*.mdx`）と模範解答（`solutions/`）
5. `node scripts/taught.mjs <章の最初の節の id>`（例や問題を足す・変えるときに、使ってよい書き方を確かめる）

## 2. 何を直すか

| 指摘 | 扱い |
|---|---|
| L（学習者の目）の指摘 | **採否の決定に書いてあるとおりに直す。** 決定に「採らない」とあるものは触らない。決定に出てこない L の指摘は触らない |
| J（日本語）の指摘 | 決定に「採らない」と書いていないものは、全部直す。報告の「直し」の文をそのまま使ってよい。**直しの文のほうが悪い、意味が変わる、と思ったら直さずに報告する** |
| どの章でも直すもの | 下の第3章 |

読み手は原稿だけを読んでいる。組む問題（`<Input>` `<Output>` のある形）では、画面が判定のケース1から入力例と出力例を自動で出すので、「形は出力例のとおりです」はそのままでよい。「出力例が無い」という指摘は、古い形（`<Input>` `<Output>` が無い）の問題のときだけ採り、新しい形に直す。

読み手は答えを知らない人として読んでいる。「説明が足りない」と言われた所に文を足すときは、**足りないものを一文で足す**。段落を足さない。

## 3. どの章でも直すもの

読み手が挙げていなくても、見つけたら直す。

- **画面に出ない印を指す文。** 「上の「説明」」「「やってみる」の例」「「困る例」」は、原稿の印の名前で、画面には出ない。画面に見えているもので指し直す（「この節の最初のコード」「上の表」「2行目の `if`」）
- **節の終わりの、中身の無い文。** 「〜できるようになりました。」「〜を見ました。」を消し、次の節の予告だけ残す。予告も中身が無ければ消す（そのとき `{/* つながり */}` の印ごと消してよい）
- **作り手の言葉。** 学習者、読者、通し課題、組む・変える、この節の狙い
- 節の中の表記のゆれ（「くり返す」と「繰り返す」など。その節で多いほうにそろえる）

## 4. 変えてはいけないもの

- 節の `id`・`chapter`・ファイル名、課題の `id`。**問題の中身を替えるときも、課題の id はそのまま使う**
- 課題を消すのは、決定に「消す」と書いてあるときだけ。消したら、その模範解答のファイルも消す
- その章で教える内容と順番。足りない例を足す、問題を替える、は決定に書いてある範囲だけ
- `scripts/`、`design/`（報告を除く）、`src/lesson/`、ほかの章の `.mdx`。構文の一覧・台帳・用語集に足すものは、足さずに報告に書く
- 節の本文で「第N章M節」と書いた参照は、行き先が実在すること（検査20）

## 5. 問題を替える・足すとき

- 模範解答を先に書き、1行ごとに、同じ形が `taught.mjs` の出力かその節の例にあることを確かめる
- 模範解答が出しているものは、全部問題文に書く。組む問題は `design/spec/10-lesson-and-writing.md` 第3.11節の形（問題文・`<Input>`・`<Output>`）にする
- 練習問題（書き換える）は、例と別の変数・別の数で作る。例の値を写して通る問題にしない
- `<Run>` の `out` は実際の実行結果を書く（`build:tests` が照合する）

## 6. 検査

```
npm run build:tests
npm run check:lessons
```

- 「不合格」のうち、自分の章のものは直す。**ほかの章は別の人が同時に直しているので、ほかの章の不合格は無視してよい**（報告に一行書く）
- 「目安から外れている所」は、読みやすさを見て決める。目安に合わせるために文を切ったり足したりしない
- git の commit・push はしない。開発サーバは起動しない。**git で作業ツリーを書き換える命令（`git checkout`、`git restore`、`git reset`、`git stash`、`git clean`）は使わない。** ほかの人の直しは commit されていないので、消えると戻せない（2026-10-02 に、直す人が `git checkout -- .` で1章ぶんを消した）。自分の直しをやり直したいときは、ファイルを開いて手で戻す。Chrome を終わらせるときに `taskkill /F /IM chrome.exe` を使わない

## 7. 報告

`design/reviews/<章>-fixed.md` に書く。最後の返答は短くてよい（直した数、直さなかった指摘、検査の結果）。

```
## 直した
- L3: （何をどう直したか。一行）
- J1〜J12: 直した（まとめてよい）

## 直さなかった（理由）
- J7: 直しの文だと意味が変わるため

## 節ごとに変えた問題
| 課題の id | 前 | 後 | なぜ |

## 構文の一覧・台帳・用語集に足すもの

## 目安を外したままにした所と理由

## 検査の結果（自分の章に関わる行をそのまま）
```

## 8. 2回目の直し

1回目の直しのあと、読み手2人がもう一度読んだ報告（`design/reviews/<章>-learner2.md` と `<章>-japanese2.md`）を見て直すときの形である。採否の下書きは無い。次の決まりで自分で決める。

| 指摘 | 扱い |
|---|---|
| J（日本語） | 直す。直しの文のほうが悪い・意味が変わる・内容を足している、と思ったら直さずに報告する |
| L の「止まる」、事実の誤り（行番号が合わない、実行結果と本文の数が合わない、指している節に書いていない） | **自分で確かめてから**直す。直し方は軽い順: 模範解答を教えた書き方だけで書き直す／問題文・ヒントの一文を直す・足す |
| L の「引っかかる」 | 一文の言い直しで直るものだけ直す |
| L の「要らない文」 | 消す。消すと情報が無くなる文は残す |
| 例や問題を足す・替える・消すことが要るもの、教える順番に関わるもの | **直さない。**「本体に確かめる」に書く |
| `design/reviews/_cross.md` の「採らない指摘」に当たるもの、1回目の採否（`<章>-decision.md`）で「採らない」と決めたものと同じ指摘 | 直さない |

報告は `design/reviews/<章>-fixed2.md` に書く。形は第7章と同じで、最後に「本体に確かめる」を足す。
