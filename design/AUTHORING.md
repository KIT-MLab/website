# 教材の作り方

章を新しく書くとき、書いた章を直すときに、最初に読む。
ここに書くのは**誰が・どの順に・何を見て作るか**である。書式と細かい決まりは `spec/10-lesson-and-writing.md`、画面と検査の仕組みは `spec/20-platform.md` に残す。食い違ったら、この文書を先にする。

作成: 2026-10-02

---

## 1. 目指すもの

1. **学習者にとって、分かりやすく使いやすい**
2. 運営しやすい（1 の次）

決まりも検査も、1 のための手段である。**決まりを守ると 1 が悪くなるときは、決まりを外して理由を残す。**

「分かりやすい」は、学習者の席から見た次の6つで確かめる。どれも「決まりに合っているか」ではなく「読んだ人がどうなるか」を聞いている。

| # | 問い |
|---|---|
| 1 | この節を読むのに要るものを、学習者はもう全部持っているか（まだ教えていない書き方・語・考え方が、説明にも問題にも出てこないか） |
| 2 | 何のための節かが、説明を読む前に分かるか |
| 3 | 例から問題までの段差は、1人で越えられる高さか |
| 4 | 読まなくてよい文、解かなくてよい問題が混ざっていないか |
| 5 | 人が人に説明するときの日本語になっているか |
| 6 | 全部の文が学習者に向けて書かれているか（作り手どうしの言葉が、学習者に見える所に出ていないか） |

## 2. これまでの失敗の出どころ

2026-10-02 に、検査を全部通って公開されている4つの節を、この文書の読み手（第5章）に読ませた。4節すべてで直すべき所が見つかり、2節には学習者が進めなくなる所があった。

| 失敗 | 見つかった例 | 出どころ |
|---|---|---|
| まだ教えていないことを問題で使わせる | 第3章4節の閏年。「割り切れる」を `% 4 == 0` と書く形も、`and` と `or` を `()` でまとめる形も、どこにも例が無い | 書き手は Python を知っているので気づかない。検査16 が見るのは台帳にある書き方（`for` を使ったか）までで、**使い方の組み合わせ**は見えない |
| 問題文のとおりに書くと落ちる | 第13章2節の演習。模範解答は行の頭に学習率を出すが、問題文に書いていない | 書いた人も採る人も、答えを知ったうえで問題文を読んでいた。**答えを知らずに解く人**がいなかった |
| 意味のない問題・文 | 第3章4節の練習問題1（すぐ上の例の値を写せば通る）。節の終わりの「〜できるようになりました。」が99節中67節 | 数と枠を決まりにした。枠（つながり）があるので埋めた |
| 不自然な日本語 | 「1つのifでまだ書けません」「値は増えてしまいました」（何の値か書いていない） | 日本語だけを見る人がいなかった。検査が見るのは字数と禁止語で、読めるかどうかではない |
| 作り手の言葉が学習者に見える | 「上の「説明」を見直してください」が15か所、「「やってみる」の例では」が約45か所。「説明」「やってみる」は原稿の中の印で、画面には出ない。ほかに「通し課題」、登録画面の「他の学習者には見えず」 | 設計で使う言葉と、画面に出す言葉を分けていなかった |
| 型どおりに作りすぎる | 第13章2節の「困る例」は、困る場面ではなく数字の羅列 | 「1つでも×なら不合格」のチェックリスト。設計の表にも「困る例」「組む課題」の欄があり、設計の段でもう枠を埋めていた |

共通する根は2つある。

- **直し方が「失敗 → 決まりを足す → 検査を足す」だった。** 決まりが増えるほど、書き手は決まりを満たすほうを向き、学習者から離れる。下限は水増しを生み、枠は埋め草を生んだ（`HANDOFF.md` 第4章に6回ぶんの記録がある）
- **学習者の目が入るのが、最後の利用者の確認だけだった。** いちばん数の少ない人に、全部の発見を頼っていた

だからこの体制では、**学習者の目を、作る前（設計メモ）と採る前（読み手）の2か所に置く。** 決まりは増やさず、種類を分けて軽くする。

## 3. 決まりは3種類に分ける

| 種類 | 何か | 見るもの | 破れたら |
|---|---|---|---|
| **事実** | 正しいか誤りかが決まるもの。コードが動く、実行結果が合う、模範解答が通る、何もせずには通らない、台帳より先の書き方を使っていない、参照先の節がある、語が用語集にある | 機械（`npm run build` が止まる） | 直すまで出さない |
| **目安** | たいていはそのほうが良いが、外したほうが良い場合もあるもの。1文の長さ、段落の文の数、字数、使わない言い回し、節の並び（困る例 → やってみる → 説明） | 機械が「目安」として知らせる。**止めない** | 外したままにするなら、書き手が報告に理由を一行書く。採る人が決める |
| **判断** | 読まないと分からないもの。第1章の6つの問い | 読み手（第5章）と採る人 | 採る人が決める |

- **下限と「必ず置く」は、新しく作らない。** いま残っているのは「節ごとに演習問題（組む）を1問」だけで、これも frontmatter の `nobuild` に理由を書けば外せる
- 目安を満たすために文を足したり切ったりしない。**満たすために書き換えた文は、満たしていない文より悪い**
- `spec/10` 第8章のチェックリストの「1つでも × があれば不合格」は、事実に当たる項目だけに当てはめる

`check:lessons` の検査のうち、目安として扱うもの: 検査6（1文60字）・7（1段落3文）・8（本文800字、説明100〜600字）・9（使わない言い回し）・10（抽象語）・11（感嘆符）。

## 4. 流れ

```
①学習者の像 → ②設計メモ → ③書く → ④機械の検査 → ⑤読む（2人）→ ⑥採る → ⑦利用者が解く → ⑧指摘を扱う
   （部ごと）     （章ごと）   書き手     事実だけ止める    仕様を知らない人   Claude本体    準備中のまま      第6章
```

| 段 | 誰が | 何をするか | 出てくるもの |
|---|---|---|---|
| ① 学習者の像 | Claude 本体 | 部を組む前に、その時点の学習者が「確実にできる／あやふや／まだ出会っていない」を根拠つきで書く | `spec/35-learner-after-ch7.md` と同じ形の文書 |
| ② 設計メモ | Claude 本体 | 節ごとに、分かってほしいこと・持っているもの・新しく出すもの・確かめること（＝問題）を決める。**問題の数はここで決まる。** 形は `authoring/brief-template.md` | `design/briefs/<章>.md` |
| ③ 書く | 書き手（Sonnet） | 設計メモのとおりに書く。**設計メモに無い問題・語・書き方を足さない。** 足したい・減らしたいときは、書かずに報告する。指示は `authoring/writer.md` | 節の `.mdx`、模範解答、報告 |
| ④ 機械の検査 | 機械 | `npm run build:tests` → `npm run check:lessons` | 事実の誤り（止まる）と、目安の知らせ |
| ⑤ 読む | 読み手2人。**仕様書も設計メモも渡さない** | 学習者の目（`authoring/reader-learner.md`）と、日本語（`authoring/reader-japanese.md`） | 止まる所・引っかかる所・要らない所・直した文の案 |
| ⑥ 採る | Claude 本体 | 読み手の指摘を1つずつ確かめて、直す・直さないを決める。直したら ⑤ をもう一度（2往復まで）。残った迷いは「見てほしい所」に書く | 直した節、`design/briefs/<章>.md` の末尾の「見てほしい所」 |
| ⑦ 解く | 利用者 | 準備中のまま全部の問題を解き、気づいたことを節の画面のメモに書く | メモ |
| ⑧ 指摘を扱う | Claude 本体 | 第6章の順に扱う | 直した教材、実例集・台帳・設計メモの問いへの追記 |

書いてある章を直すときは、⑤ から入る。直す量が多い節だけ ② に戻って設計メモを書く。

### 4.0 書いてある章をまとめて直すときの形（2026-10-02 に全章でやった形）

章ごとに、次の順で回す。指示のファイルは `design/authoring/`、出てくるものは `design/reviews/` に置く。

| 順 | 誰が | 指示 | 出てくるもの |
|---|---|---|---|
| 1 | 読み手2人（章を通して読む） | `reader-learner.md`・`reader-japanese.md` の「章をまとめて読むとき」 | `<章>-learner.md`（L1…）、`<章>-japanese.md`（J1…） |
| 2 | 採否の下書き（Opus） | `decider.md`。読み手の指摘を1つずつ確かめる | `<章>-decision.md` |
| 3 | Claude 本体 | 下書きの「本体に確かめる」に答え、末尾に「本体の決定」を書く。章をまたぐ決定は `_cross.md` に足す | 同じファイルの末尾 |
| 4 | 直す人（Sonnet） | `fixer.md` | 直した章、`<章>-fixed.md` |
| 5 | 読み手2人がもう一度読む | 1 と同じ | `<章>-learner2.md`・`<章>-japanese2.md` |
| 6 | Claude 本体が決めて、直す人が仕上げる | `fixer.md` 第8章「2回目の直し」 | `<章>-fixed2.md` |

やってみて分かったこと。

- **同時に動かすのは3つまで。** 20まで出せるが、検査（`build:tests`）が同じファイルを書くので、多いと互いの途中の状態で落ちる。利用の上限にも早く当たる
- **commit していない間は、作業ツリーを書き換える git の命令を誰にも使わせない。** 直す人の1人が `git checkout -- .` で1章ぶんの直しを消した。区切りごとに、作業ツリーの写しを別の場所に取る
- **2回目の読み直しは省かない。** 1回目の直しが新しい穴を作る（例の値を写せば通る練習問題、ヒントが別の解き方へ誘導、決定の文をそのまま入れて長くなった段落）。2回目で「進めなくなる所」はどの章も0になった
- **採否の下書きは Opus に任せてよいが、「本体に確かめる」は必ず読む。** 章の内容・順番・画面の言葉に関わるものが、そこに集まる
- **読み手は、原稿に無くて画面にあるもの（入力例・出力例、「この節の書き方」の表）を知らない。** `_cross.md` に「画面が自動で出すもの」を書いておくと、誤報が減る
- **判定の限界から来る指摘（出力を直接 `print` すれば通る、など）は毎回出る。** 採らないと先に決めて `_cross.md` に書く

### 4.0.1 練習問題集を書くとき

練習問題集（`src/content/practice/`）は説明を書かないので、設計メモの代わりに `authoring/practice-writer.md`（1つの話題に★1×2・★2×2・★3×1、模範解答を先に書く、問題文だけから別の書き方で解き直す）を書き手に渡す。書いたあとは、節と同じく、仕様を知らない読み手に読ませてから採る。

### 4.1 同じ1枚を見る

設計する人・書き手・読み手は、**「この節の時点で学習者が持っているもの」について同じ1枚を見る。**

```
node scripts/taught.mjs <節の id>
```

その節より前に教えた書き方（構文の一覧）、導入ずみの台帳、出した語と、その節で教えるもの、まだ教えていないものが出る。
ここに無い書き方は「教えた」と言えない。**教えたはずなのに出てこないなら、構文の一覧（`src/lesson/syntax-list.ts`）か台帳（`scripts/python-tools.mjs`）に足す。** そうすれば節の「この節の書き方」の表にも出て、学習者も同じものを見られる。

### 4.2 読み手に渡さないもの

読み手には、仕様書・設計メモ・書き手の報告を渡さない。渡すと、作り手の意図で読んでしまい、学習者が止まる所を通り過ぎる。
読み手が見るのは、学習者が見るもの（節の本文と問題）と、`taught.mjs` の出力と、模範解答だけである。

### 4.3 読み手の使い分け

| 読み手 | モデル | 理由 |
|---|---|---|
| 学習者の目 | 新しく書いた章と第2部以降は Opus。第1部の見直しは Sonnet でよい | 試した4節で、どちらも主な欠陥は見つけた。Opus は自分でコードを動かして確かめ、Sonnet が見逃した1件（通る値が飛び飛びにしか無い問題）を見つけた。Sonnet は誤報が1件あった（教えてある `int(input())` を未習とした） |
| 日本語 | Sonnet | 試した4節で、Opus とほぼ同じ文を挙げた |

**読み手の指摘もそのまま採らない。** 「止まる」は採る人が自分で確かめる（教えた節を開く、コードを動かす）。読み手は「ヒントを足す」のような足し算を勧めがちで、足す前に「無くても進めるか」を見る。

## 5. 読み手が見ること

| 読み手 | 見ること | 見ないこと |
|---|---|---|
| 学習者の目 | 上から読んで止まる所。模範解答の1行ごとに「その書き方をどこで見たか」を挙げ、挙げられない行を未習とする。例から答えまでに自分で考えることの数。その節で教えたことを使わずに通る道。その問題を消したら何を確かめられなくなるか。消しても何も失わない文 | 決まりに合っているか |
| 日本語 | 語順、主語や目的語の抜け、ぶつ切り、硬い言い方、言葉の選び、中身の無い文、あいまいな指示、表記のゆれ、**学習者に向けていない文**。引っかかった文には直した文を付ける | 内容が正しいか、順番がよいか |

どちらも「見つからなければ無しと書く」。数を求めると、読み手も水増しする。

## 6. 指摘の扱い方（決まりを足す前に）

利用者や読み手から指摘が来たら、上から順に扱う。**下へ行くほど重く、あとで副作用が出やすい。**

1. **その箇所を直す**
2. **同じものが他に無いか探す。** 言葉なら全文を検索する。形なら、その観点だけを読み手に渡して他の章を読ませる。見つかった数を記録する
3. **出どころを決めて、いちばん軽い置き場所に残す**

| 出どころ | 置き場所 |
|---|---|
| 書き手が、どう書けばよいか知らなかった（言い回し、問題文の書き方、作り手の言葉） | `authoring/examples.md`（直す前と直した後の実例）。決まりの文より、実例のほうが書き手に効く |
| 設計の段で考えていなかった（確かめることが決まっていない、段差を見ていない） | `authoring/brief-template.md` の問いを1つ足す |
| 教えた範囲が見えていなかった | 構文の一覧・台帳・用語集に足す（`taught.mjs` に出るようになる） |
| 機械で確実に見分けられる誤り | 検査を足す。**先に実際の教材で誤報を数える**（`HANDOFF.md` 第4章） |
| 上のどれでもない | `spec/10` に決まりを足す。**下限と「必ず置く」の形にはしない** |

4. **何をどこに残したかを、`DECISIONS.md` に1行書く**（利用者の判断が入ったものだけ）

`spec/00-overview.md` の冒頭にある「その箇所だけの話か、全体の基準か」の二択は、この表に置き換える。「基準なら仕様書に足す」を続けた結果が、いまの決まりの量である。

## 7. 誰が何を持つか

| 人 | 持つもの |
|---|---|
| 利用者（プロジェクトの代表） | 何を教えるか、どの順に教えるか、画面に出す言葉の最終の判断。準備中の章を解いて公開する |
| Claude 本体 | 学習者の像、設計メモ、採否、指摘の扱い。**書き手と読み手の出したものを、そのまま採らない** |
| 書き手（Sonnet） | 設計メモのとおりに本文・問題・模範解答を書く。設計は変えない |
| 読み手（学習者の目・日本語） | 学習者として読んで報告する。直さない |
| 機械 | 事実を止める。目安を知らせる |

## 8. 運営のしやすさ（後回し。いま決めてあることだけ）

- **利用者に渡すのは「見てほしい所」の一覧にする。** 章ごとに、採る段で迷った所・目安を外した所・課程を変えた所だけを `design/briefs/<章>.md` の末尾に並べる。利用者は全部解くが、どこを疑って読めばよいかが先に分かる
- **利用者のメモは第6章の順に扱う。** 直した所と、他の章で同じものを何件直したかを返す
- 公開ずみの章を直すと、進み具合の記録（課題の id）に響くことがある。**課題の id を変える・問題を消すときは、先に利用者に確かめる**
