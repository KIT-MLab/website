## 2. 本文の書式

### 2.1 ファイルの置き方

```
src/content/lessons/
  00-start/
    01-pc.mdx
    02-how-to-use.mdx
  01-python/
    01-print.mdx
    ...
```

ディレクトリ名が章、ファイル名が節。番号順に並ぶ。

### 2.2 frontmatter

```yaml
---
id: python-01-print          # 全体で一意。進度の記録に使う
chapter: 01-python
title: print文で値を表示する
minutes: 12                  # 想定所要時間
terms: [print, 文字列, 引数]  # この節で初出の用語。用語集に登録済みであること
nobuild: 理由                 # 任意。「組む」課題を置かない節だけ書く（検査15）
---
```

### 2.3 本文で使う部品

Markdown に加えて、次の部品だけを使う。これ以外の独自部品を足さない。

| 部品 | 用途 |
|---|---|
| `<Run>` | その場で実行できるコード例。実行結果を下に出す。**エラーそのものが題材の節では `out` の代わりに `error` を書く**（第6.1節）。ビルド時に、本当にそのエラーで止まるかを確かめる |
| `<Mistake>` | よくある間違い。壊れたコード・エラーメッセージ・直し方の3つを持つ |
| `<Exercise>` | 課題。エディタと採点ボタンを出す |
| `<Level0>` | レベル0でだけ開いた状態で出る操作の補足 |
| `<Keys>` | 日本語配列のキーボードの図。`highlight` に渡した記号のキーと、`Shift` が要るかどうかを示す。**`<Level0>` の中にだけ置く**（第11.7節）。第0章の記号の節のためのもので、ほかの章では使わない |
| `<Figure>` | コードの一部に罫を引いて、計算や変換の順番を示す図。渡すのは「どの部分か」を表す文字列だけで、位置は部品が数える（`10-lesson-and-writing.md` 第11.4節）。見つからない・2か所ある・半角でない文字がある、のどれかならビルド時に落ちる |
| `<Experiment>` | 図・実験を埋め込む（第4部以降で使う） |

書き方の例:

```mdx
<Run>
print("Hello")
</Run>

<Mistake code={`print(“Python”)`} error={`SyntaxError: invalid character '“' (U+201C)`}>
全角のダブルクォートを使っています。`"` は半角で入力してください。
</Mistake>

<Exercise id="python-01-print-b1" kind="build" ...>
3つの数を受け取り、いちばん大きい数を返す関数 `largest` を書いてください。
</Exercise>
```

### 2.4 規約の自動検査

`scripts/check-lessons.mjs` を作る。全 `.mdx` を読み、`10-lesson-and-writing.md` 第8章のチェックリストのうち機械判定できるものを検査する。

検査する項目:

1. 要素の順序（困る例 → やってみる → 説明 → よくある間違い → 課題 → つながり）。「課題」と「つながり」は無くてよい
2. `<Run>` が「説明」より前にあること
3. `<Mistake>` が1〜3個
4. `<Exercise>` が0〜7個。型ごとの書き方が揃っていること（`10-lesson-and-writing.md` 第3.8節）
5. `kind="build"` の `tests` に3件以上の入力があり、境界（0・負・同値・空のいずれか）を含むこと
6. すべての文が60字以内（句点で区切って数える。コードブロックと表は除く）
7. すべての段落が3文以内
8. 本文が800字以内、「説明」が250〜600字（第0章は100〜400字）。**本文に下限は置かない**（水増しを招くため。第4.1節）
9. 禁止表現（`10-lesson-and-writing.md` 第4.2節）を含まないこと
10. 抽象語の言い換え（第4.3節の左列）を含まないこと
11. 本文に `！` を含まないこと
12. `terms` の全語が用語集にあること
12.5. 「選ぶ」課題が3問以上あるとき、正解が全部同じ位置でないこと
13. `<Level0>` に概念の説明の言い回し（`とは` `と呼び` `のことです` 等）が無いこと
14. 用語の言い換えを選ばせる問いが1節に2問以上ないこと（第3.7節）
15. **節ごと**に「組む」が1問以上（第0章は「打つ」と「選ぶ」）。置かない節は frontmatter の `nobuild` に理由を書く（第3.8節）。**課題の総数に下限は置かない**
16. **まだ教えていない Python の道具**をコードで使っていないこと。台帳は `scripts/python-tools.mjs`
17. 台帳が中身とずれていないこと（導入する節と書いてあるのに、その節に一度も出てこない道具がないか）
18. **まだ出てきていない語**を地の文で使っていないこと。用語集の「初出の章」より前の章で使っていたら落とす
19. **問題文に答えのコードが書かれていない**こと（第3.9節）。模範解答から `starter` を引いた残り（数・文字列・演算子）が、すべて問題文の中のコードに出てくるなら落とす
20. 学習者が読む文章の、節への参照が「第N章M節」の形で、行き先が実在すること（第15.2節）
21. **章のディレクトリが、どれか1つの部に属していること**（第17.1節）。部の表は `scripts/parts.mjs`

16〜18は「書き手が知っているせいで気づけない誤り」を捕まえるためのものである。書き手は自分が知っている道具や語を、教える前に使っても違和感を持たない。読み手は詰まるが、何が足りないのかを言葉にできない。**人の目では見つけにくく、機械なら確実に見つかる。**

**18 は章の単位でしか見られない。** 用語集の「初出の章」が章だからである。同じ章の中で、後の節の内容を前の節が使っていても落ちない（第7.2節が第7.3節の2次元配列を使っていた）。**章の中の順番は台帳（16）でしか見られない**ので、節をまたいで効く道具は台帳に登録する。

16 と 18 で見る範囲が違う。16 は**学習者が動かすコード**だけを見る（コードにある道具は読み手が真似して動かすため）。18 は**地の文**だけを見る（コードブロックと部品の属性は落とす。英語のエラーメッセージに `not` や `int` が混ざるため）。

19 は別の種類である。書き手が**枠を埋めた**誤りを捕まえる。問題文に答えを書いた課題は、書いた本人には課題に見える。読み手にとっては書き写しである。第1〜3章で18問見つかった（第3.9節）。

**この検査はビルドの前に走らせ、失敗したらビルドを止める。**

## 3. Python の実行

### 3.1 動かし方

- Pyodide を Web Worker で動かす。UI を止めない
- 初回は約10MB の読み込みが要る。**最初の1回だけ、進捗の出るバーを出す**。2回目以降はブラウザのキャッシュから
- **numpy のような外部のパッケージは、コードの `import` を見て要るときだけ読む**（`loadPackagesFromImports`）。使うのは第7章だけなので、第0〜6章の読み込みを重くしない。配り元は Pyodide 本体と同じ CDN
- ページを開いた時点では読み込まない。**最初に ▶ を押したときに読み込む**
- 1回の実行の上限は**5秒**。超えたら止めて「時間がかかりすぎたので止めました。無限ループになっていないか確認してください」と出す
- 実行ごとに変数を引き継がない。1つの `<Run>` や `<Exercise>` は独立して動く

### 3.2 `input()` の扱い

既存の Colab 教材は `input()` を多用していた。ブラウザの `prompt` は使わない。

- コード欄の下に**「入力」欄**を置く。複数行書ける
- `input()` はこの欄を上から1行ずつ読む
- 行が尽きたら `EOFError` ではなく、「入力欄が空です。入力欄に値を書いてから実行してください」と出す
- 課題の採点では、入力欄の中身も採点側が指定する

### 3.3 使えるライブラリ

標準ライブラリと `math`、`random`、そして**第7章から `numpy`**。`matplotlib` は使わない（図はこちらで描く）。

以前は「第1部では numpy を使わない」と書いていたが、`30-python-curriculum.md` の課程表は第7章（第1部の最後）の全節を numpy に当てている。仕様書どうしが食い違っていたので、課程表のほうに合わせた（2026-09-21）。第7章が**機械学習への橋**であり、第2部の入口が配列になるためである。

`random` を使う課題では、採点時に種を固定する。

## 4. 演習と採点

### 4.1 課題の型

```ts
type Exercise = {
  id: string;
  kind: 'trace' | 'modify' | 'build';
  prompt: string;           // 問題文（mdx の中身）
  starter?: string;         // modify で渡す動くコード。build では渡さない
  stdin?: string;           // 入力欄の初期値
  tests: Test[];
  hints: string[];          // 段階的に出すヒント。0〜3個
  mistakes: string[];       // この課題で当てはめる「よくある間違い」の id
};

type Test =
  | { kind: 'stdout'; stdin?: string; expect: string }        // 出力の一致
  | { kind: 'call'; fn: string; args: unknown[]; expect: unknown }; // 関数の呼び出し結果
```

### 4.2 期待値の作り方

**模範解答をブラウザに配らない。** 代わりに、ビルド時に模範解答を実行して `expect` を埋める。

- 模範解答は `src/content/lessons/**/solutions/*.py` に置く。**このディレクトリはビルド成果物に含めない**
- `scripts/build-tests.mjs` が模範解答を実行し、`expect` を持つテスト定義を生成する
- 生成物だけがブラウザに渡る

模範解答をここで全部読むので、**使い回しの照合もここでやる**（`10-lesson-and-writing.md` 第3.5節）。

**`starter` もここで実行する。**「変える」課題の `starter` をそのまま走らせた出力が `expect` と一致したら不合格にする。読み手が1文字も直さずに通る課題だということである（第3.9節）。実際に1問あった（第2章「整数と小数」）。問題文を読んだだけでは気づけないので、ここで走らせて見る。
同じ節で2つの課題の模範解答が同じなら不合格。「組む」の模範解答がその節の `<Run>` か例題の
「打つコード」と同じでも不合格。比較は空白と改行の違いを除いて行う。

### 4.3 採点の流れ

1. 学習者のコードを Pyodide で実行する
2. `tests` を順に走らせる
3. 全部通れば合格。1つでも落ちたら不合格
4. 不合格のとき、次の順で応答を選ぶ
   1. **実行時にエラーが出た場合**: その節の `<Mistake>` の `error` と照合する。前方一致すれば、その `<Mistake>` の説明を出す
   2. 照合しない場合: エラーの型（`NameError`、`SyntaxError` 等）ごとの一般的な説明を出す
   3. **エラーは出ないが結果が違う場合**: 最初に落ちたテストの入力と、期待した値と、実際の値を並べて出す
5. 3回落ちたら `hints` の1つ目を出す。以降1回落ちるごとに次のヒントを出す

**単なる「不正解」だけを返してはいけない。** `00-overview.md` 第3.3節の受け入れ条件。

### 4.3.1 模範解答の開示

**通したあとだけ見える。** 合格すると、その課題に「別の書き方を見る」が出る。

- 模範解答は `/api/solution/:exerciseId` から取る。**その利用者にその課題の合格済みの提出があるときだけ返す**
- ビルド成果物に模範解答を含めない（第4.2節）ので、通す前に読み出す手段はない
- ログインしていない人は合格を記録できないため、模範解答も見られない
- 落とした回数では開かない。待てば見えると分かると、考えるのをやめる人が出る
- **押されたときに、未送信の提出を先に送りきる。** 提出は30秒ごとと節を離れるときに送るので（第6.1節）、通した直後に押すとまだサーバに届いていない。そのまま尋ねると、通したのに「通したあとに読めます」と返る。送りきれなかったときは尋ねずに「いまは通信ができていないため、模範解答を取り出せません。」と出す
- 2026-09-14 まで、ここは画面が付ける `?passed=1` を信用していた。申告は偽れるので制限として働いていなかった

### 4.4 判定の緩さ

- 出力の比較は、**行末の空白と末尾の改行を無視**する
- 数値の比較は、浮動小数点なら相対誤差 `1e-9` まで許す
- **模範解答と違う書き方でも、テストが通れば合格**とする。書き方の指定は問題文に書いた範囲（「`max` は使わないでください」など）だけを、提出コードの文字列検査で確認する

### 4.5 記録

採点を走らせるたびに、**提出されたコードと結果を D1 に記録する**。運営が読むため。

## 5. アカウント

### 5.1 方針

外部にも公開する。内部（勉強会のメンバー）と外部（見に来た人）を見分けられること。重い本人確認はしないが、簡単ななりすましは防ぐ。

### 5.2 登録

1. 招待コード（例: `MLAB-2026`）を入力する
2. 表示名を決める
3. サーバが**利用者ID**（例: `u_7QK3M9`）と**パスワード**（6桁の数字）を発行し、画面に出す

> **2026-09-14: 「合言葉」を「パスワード」に改めた。** `10-lesson-and-writing.md` 第4.3節「名前があるものは名前で呼ぶ」に反していたため。これは世の中でパスワードと呼ばれているものであり、言い換える理由がない。「利用者IDとパスワード」なら、はじめて見る人にも何を聞かれているかが説明なしで分かる。
4. 「控えました」を押すと先へ進む

招待コードは運営が発行する。コードごとに**所属**（内部 / 外部）と、既定のロール（学生）が決まる。

**外部から来た人も登録して全機能を使える。** サイトに常設の公開コードを1つ置き、学習ページから登録できるようにする。採点も進度の保存も内部の学生と同じ。運営の画面では**内部と外部を別のタブに分け、既定では内部だけを表示する**。

最初に登録する招待コードは次の2つ（2026-09-14 決定）。

| コード | 所属 | 用途 |
|---|---|---|
| `MLAB-2026` | 内部 | 勉強会のメンバー |
| `MLAB-OPEN` | 外部 | サイトに常設。学習ページから誰でも登録できる |

### 5.2.1 招待コードは cohorts と別のテーブルに持つ（2026-09-25 決定）

`migrations/0002_cohorts.sql` はこの公開リポジトリに入っている。招待コード自体が
`cohorts.code`（所属の主キー）だと、内部の招待コード `MLAB-2026` がそのまま世に出てしまう。
`cohorts.code` は `users.cohort_code` / `meetings.cohort_code` から参照されているので、
所属のIDとしては変えられない。招待コードを別のテーブルに出す。

```sql
CREATE TABLE invite_codes (
  code        TEXT PRIMARY KEY,
  cohort_code TEXT NOT NULL REFERENCES cohorts(code),
  open        INTEGER NOT NULL DEFAULT 1,  -- 0 なら登録には使えない（閉じたコード）
  created_at  INTEGER NOT NULL
);
```

- **登録（`/api/register`）は `invite_codes` を `open = 1` で探し、そこから `cohort_code` で
  所属を引く。** `cohorts.code` を直接は引かない
- 存在しないコードと、閉じている（`open = 0`）コードは、**まったく同じ**「招待コードが違います。」
  で断る。コードが存在することを教えない（第5.6節の `field` の考え方と同じ）
- `migrations/0007_invite_codes.sql` に `MLAB-OPEN`（開いたまま）と `MLAB-2026`（閉じて）を
  入れてある。`MLAB-2026` は 0002 で既に公開リポジトリに書かれてしまっているので、
  ここでは閉じる
- **実際にメンバーへ配る内部の招待コードは、このリポジトリには一切書かない。**
  本番と開発、それぞれのデータベースへ、運営が `wrangler d1 execute` で直接1行足す。
  閉じるときも同じ道具で `open` を0にする。手順は `90-cloudflare-setup.md`
- 1つの所属（`cohorts`）に複数の招待コードを対応させられる。増減させるのは `invite_codes`
  の行だけで、`cohorts` の行自体（所属のID・内部/外部の区別・表示名）は変わらない

### 5.3 ログイン

- 登録した端末は、署名付き Cookie で自動的にログインした状態になる（有効期間180日）
- 別の端末では、**利用者ID とパスワード**で入る
- パスワードを忘れた場合、運営が管理画面から再発行する

**再発行の実装（2026-09-25）**: `/staff/user/<利用者ID>` の「パスワードを作り直す」ボタン。
口は `POST /api/staff/user/:id/passcode`（第7章）。新しい6桁は応答の1回だけ返し、
`fail_count`/`retry_after` を0に戻し、その利用者の `sessions` を全部消す（ログイン中の端末も
ログアウトする）。範囲は第8.4節の `userDetail` と同じ。加えて、**誰も自分自身のパスワードは
ここでは作り直せず**、**管理者でない運営は管理者のパスワードを作り直せない**（管理者だけができる）。

**パスワードを外すほど待たされる（2026-09-14 決定）。** パスワードは6桁の数字で100万通りしかない。利用者IDを知っている人が機械で片端から試せば1日ほどで当たる。同じ利用者IDでの失敗を数え、次に試せる時刻を延ばす。

| 続けて外した回数 | 次に試せるまで |
|---|---|
| 1〜2回 | すぐ |
| 3〜4回 | 30秒 |
| 5〜7回 | 5分 |
| 8回以上 | 1時間 |

- **正解したら回数は0に戻る。** 打ち間違いを引きずらせない
- 待っている間は「あと◯分◯秒たってからもう一度試してください」と出す。入れたパスワードが合っていたかどうかは**出さない**
- 待ち時間はサーバが眠って作るのではなく、`users.retry_after` に時刻を書いて即座に断る。**Worker を待たせない**
- パスワードが違うときと、利用者IDが存在しないときは、**同じ文面**（「利用者IDかパスワードが違います」）を返す。どちらが違うかを教えない
- ただし**応答の速さは揃えない。** パスワードの照合は PBKDF2 を10万回まわすので100ミリ秒ほどかかり、IDが無いときは数ミリ秒で返る。揃えるには無いときにも同じだけ空回しすればよいが、それは**でたらめなIDを送るだけで Worker の CPU を食える口**になる。在るIDへの総当たりは待ち時間で頭打ちになるが、空回しには頭打ちが無い。利用者IDは32文字の字母の6桁で約10億通りあり当てずっぽうでは引けないので、速さの差は残す
- 利用者IDは**打ち直す前提**なので、前後の空白を落とし、大文字に揃えてから引く（`u_ms57cx` でも `u_MS57CX` として通る）。字母に小文字は1つも無い

### 5.4 ロール

| ロール | 記録の中の値 | できること |
|---|---|---|
| 学生 | `student` | 自分の進度と提出の閲覧。運営からのコメントの閲覧 |
| 運営 | `staff` | 自分の所属の全学生の進度・提出の閲覧、コメント、招待コードの発行、パスワードの再発行 |
| 管理者 | `admin` | 上記すべて。**運営ロールの付与と剥奪** |

> **2026-09-14: 「先生」をやめて「運営」にした。** この教材を運ぶのは教員ではなく、学生主体のプロジェクトの運営である。上級生が下級生に答える形なので、「先生」はこの場に存在しない役だった。記録の中の値も `teacher` から `staff` に変えた（`migrations/0004`）。
>
> **画面には役の名前を出さない。** 学習者にとっては答える相手が誰でも構わないので、ボタンは主語を省いて「質問する」とだけ書く。「運営」は仕様書とコードの中でだけ使う。

運営を増やす操作は管理画面の1画面で済ませる。利用者IDを入れて「運営にする」を押す。

### 5.5 扱う個人情報

**表示名だけ**。メールアドレスと本名は集めない。

**表示名には学籍番号を勧める（2026-09-14 決定）。** 登録画面に「学籍番号を入れてください」と書く。

理由は、運営の画面の行と実際の人が結びつかないと使い物にならないため。自由な名前だと、同姓の見分けも、名簿との突き合わせもできない。学籍番号は大学の名簿と照らせば個人に対応するので**匿名ではなく仮名**だが、見えるのは運営だけで、突き合わせたい相手も運営である。用途と一致している。

登録画面に**誰に見えるかを明記する**。「表示名は他の学習者には見えません。運営には見えます。」

強制はしない。欄は自由入力のままで、別のものを入れても登録できる。

### 5.6 登録とログインの画面（2026-09-14 決定）

**置き場所は学習ページ（節）の右レール。**「質問」の上に「アカウント」のブロックを足す。

| 状態 | ブロックの中身 |
|---|---|
| 入っていない | 「登録する」と「入る」の2つのボタン。見た目は `.rail__ask` に合わせる |
| 入っている | 表示名と所属の名前、「出る」のボタン |

ボタンを押すと、**本文の上にかぶせる小窓**が開く。別のページに移らないのは、読んでいた場所を失わないため。`<dialog>` を `showModal()` で開く。

#### 小窓の3つの段

1. **登録** — 招待コード / 表示名 / 「登録する」
2. **控える** — 発行された利用者IDとパスワードを出す / 「控えました」
3. **入る** — 利用者ID / パスワード / 「入る」

#### 決まり

- **段2は閉じる道を全部塞ぐ。** × を出さず、`Esc` を止め、背景を押しても閉じない。閉じる手は「控えました」だけである。**パスワードはこの1回しか出ない。**見落として閉じた人は、運営が再発行するまで別の端末から入れない
- パスワードは**3桁ずつ空けて等幅で大きく**出す（`690 399`）。紙に書き写す前提のため。利用者IDも等幅にする
- 段1と段3は `Esc` で閉じてよい
- 断りの文はその欄の下に出す。色は**琥珀**（`--l-kohaku`）。すでに「よくある間違い」で「ここが引っかかる」を表している色なので、新しい色を足さない。緑（`--l-midori`）は通った印だけに使う決まりなので使わない（第10.9節）
- **どの欄の下に出すかはサーバが決める。** 断りの応答に `field` を入れ（`code` / `displayName` / `passcode` / `uid`）、画面はそれを見て置き場所を選ぶ。**画面に文面の中身を読ませて振り分けさせない。**そうすると文面を1文字直しただけで断りが別の欄の下に出る。`field` の無い断り（登録の上限、設定不足）は、送るボタンのすぐ上の欄に出す
- ボタンは既存の `.kit-btn` / `.kit-btn--strong` を使う。**新しいボタンの形を作らない**
- パスワードの欄は `inputmode="numeric"`、招待コードの欄は `autocapitalize="characters"`。どちらも紙から打ち直すため
- 通ったら小窓を閉じ、**右レールのブロックだけ書き換える。ページを読み込み直さない**（読んでいた場所を失うため）
- 節を開いたときに `/api/me` を1回だけ呼び、その結果でブロックを塗る
- POST には `content-type: application/json` を必ず付ける（第7.1節）

#### まだ言ってはいけないこと

進度はまだ各自のブラウザにだけ保存されている（`src/lesson/store/progress.ts`）。**画面に「進度が引き継がれます」と書かない。**別の端末で入り直しても、いまの作りでは進度は付いてこない。D1 に移したら書く。

## 6. データベース

Cloudflare D1。テーブルは次の7つ。

**時刻の列はすべてミリ秒**（JavaScript の `Date.now()` の値）。秒とミリ秒が混ざると、比較したときに静かに間違うため。

```sql
-- 所属（招待コード1つにつき1行）
CREATE TABLE cohorts (
  code       TEXT PRIMARY KEY,          -- 'KIT-2026A'
  name       TEXT NOT NULL,             -- '2026年度 春'
  kind       TEXT NOT NULL,             -- 'internal' | 'external'
  created_at INTEGER NOT NULL
);

-- 利用者
CREATE TABLE users (
  id           TEXT PRIMARY KEY,        -- 'u_7QK3M9'
  cohort_code  TEXT NOT NULL REFERENCES cohorts(code),
  display_name TEXT NOT NULL,
  role         TEXT NOT NULL,           -- 'student' | 'teacher' | 'admin'
  pass_hash    TEXT NOT NULL,           -- パスワードのハッシュ
  level        INTEGER NOT NULL,        -- 0 | 1 | 2
  created_at   INTEGER NOT NULL,
  last_seen_at INTEGER NOT NULL,
  fail_count   INTEGER NOT NULL DEFAULT 0, -- 続けてパスワードを外した回数（第5.3節）
  retry_after  INTEGER NOT NULL DEFAULT 0  -- この時刻まで試せない
);

-- 節ごとの進度
CREATE TABLE progress (
  user_id    TEXT NOT NULL REFERENCES users(id),
  lesson_id  TEXT NOT NULL,             -- frontmatter の id
  state      TEXT NOT NULL,             -- 'opened' | 'done'
  opened_at  INTEGER NOT NULL,
  done_at    INTEGER,
  seconds    INTEGER NOT NULL DEFAULT 0, -- 滞在の合計
  PRIMARY KEY (user_id, lesson_id)
);

-- 課題の提出（1回の採点につき1行）
CREATE TABLE submissions (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     TEXT NOT NULL REFERENCES users(id),
  exercise_id TEXT NOT NULL,
  code        TEXT NOT NULL,
  passed      INTEGER NOT NULL,          -- 0 | 1
  failed_test INTEGER,                   -- 落ちたテストの番号
  error_type  TEXT,                      -- 'NameError' 等
  created_at  INTEGER NOT NULL
);

-- 確認問題の回答
CREATE TABLE answers (
  user_id    TEXT NOT NULL REFERENCES users(id),
  question_id TEXT NOT NULL,
  choice     TEXT NOT NULL,
  correct    INTEGER NOT NULL,
  tries      INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, question_id)
);

-- 運営からのコメント
CREATE TABLE comments (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  to_user_id  TEXT NOT NULL REFERENCES users(id),
  from_user_id TEXT NOT NULL REFERENCES users(id),
  lesson_id   TEXT,
  exercise_id TEXT,
  body        TEXT NOT NULL,
  read_at     INTEGER,
  created_at  INTEGER NOT NULL
);

-- ログインの控え
CREATE TABLE sessions (
  token      TEXT PRIMARY KEY,
  user_id    TEXT NOT NULL REFERENCES users(id),
  expires_at INTEGER NOT NULL
);
```

進度は**節を開いた時点で `opened`**、その節の課題を全部通した時点で `done` にする。

### 6.1 進度は手元に書いてからサーバへ送る（2026-09-14 決定）

進度と提出の置き場は D1（第6章）だが、**画面が読むのは常に手元の控え**にする。サーバは記録の本体、手元はその写しと送信待ちの控えを兼ねる。

```
  画面 ──書く──▶ 手元（localStorage）──送る──▶ D1
   ▲                  │
   └────── 読む ───────┘
```

こうする理由は3つある。

1. **勉強会の会場で回線が落ちても学習が止まらない。** 採点も進度も手元で完結し、繋がったときに送る
2. **読みが速い。** 節を開くたびにサーバへ問い合わせない
3. **送信に失敗しても消えない。** 送れなかったぶんは手元に残り、次に送る

送るのは第7章のとおり、**節を離れるときと30秒ごと**にまとめて。提出は採点のたび1件（第4.5節）。

入っていない人は手元に書くだけで、送らない（第9章の12）。

#### 送れたかどうかの持ち方

手元の控えに「まだ送っていない」印を持たせる。送れたら消す。**印が付いたまま残っているものだけを送る**ので、同じものを二度送らない。

#### 入ったときに手元の進度をどうするか（2026-09-14 決定）

**学習者に一度だけ尋ねる。** 入った直後、手元に進度が残っているときだけ、小窓の4つ目の段として出す。

```
  このパソコンに、入る前に進めた記録が残っています（3節）。

  これはあなたの記録ですか。

     [ はい、引き継ぐ ]   [ いいえ、捨てる ]
```

- **手元に進度が無ければ何も聞かない。** 一人で1台を使っている人は、そもそもこの段を見ない
- 「はい」→ 手元の記録をサーバへ送り、サーバの記録と合わせる
- 「いいえ」→ 手元の記録を消し、サーバの記録を手元に引き写す
- 黙って合流させないのは、勉強会で1台を別の人が使うことがあるため。**前の人の進度を自分のものにしてしまうと、運営の画面にもそのまま出る**

#### 合わせ方

| もの | 決め方 |
|---|---|
| 節の状態 | `done` が `opened` に勝つ |
| 節を開いた時刻 | 早いほうを採る |
| 滞在の秒数 | **大きいほうを採る。足さない。**同じものを二度送っても増えないようにするため |
| 課題の結果 | 提出の記録から作り直す。`passed` は1回でもあれば通ったことにする |

#### 送る口

| 経路 | 本文 |
|---|---|
| `POST /api/progress` | `{ lessons: [{ lessonId, state, openedAt, doneAt, seconds }] }` |
| `POST /api/submit` | `{ submissions: [{ lessonId, exerciseId, code, passed, failedTest, errorType, at }] }` |

**どちらも配列で受ける。** ふだんは1件、引き継ぎのときはまとめて送るが、口を2つに分けない。

提出は `(user_id, exercise_id, created_at)` を重複させない。応答が届かずに送り直したとき、同じ提出が2行になると「5回落とした」の判定（第9章の9）が狂うため。`migrations/0003` で UNIQUE を張り、`INSERT OR IGNORE` で入れる。

`GET /api/me` は節の状態に加えて**課題の結果**も返す。別の端末で入り直した人に、どの問題まで通したかを戻すため。提出の記録から `exercise_id` ごとに作る。

### 6.2 手元の控えの決まり（2026-09-14 決定）

手元の控え（`localStorage` の `kit-lesson-progress-v1`）に2つを足す。

| 足すもの | 中身 |
|---|---|
| `owner` | この控えが誰のものか。`null`（まだ誰のものでもない）か利用者ID |
| `sent` | 節ごと・提出ごとに付ける「もう送った」の印。付いていないものだけを送る |

#### 入ったとき

| `owner` | 手元の進度 | すること |
|---|---|---|
| 入った人と同じ | — | **何も聞かない。** 未送信を送り、サーバの記録を引き写して合わせる |
| `null` | ある | **尋ねる**（第6.1節の段） |
| `null` | ない | `owner` を入った人にして、サーバの記録を引き写す |
| 別の人 | — | **何も聞かず**手元を空にし、`owner` を入れ替えて引き写す。前の人の分は既にその人のサーバ側にあるので、ここで捨てても失われない |

#### 出たとき

未送信を**送りきってから**手元を空にし、`owner` を `null` に戻す。

**送りきれなかったら空にしない。** 画面に「まだ送れていない記録があるので、この端末に残しました。」と出す。回線が落ちている場に居合わせた人の記録を、出るという操作で消してはいけない。

#### 送る間隔

第7章のとおり、**節を離れるときと30秒ごと**。1操作ごとには送らない。節を離れたことは `visibilitychange` が `hidden` になったときと `pagehide` で拾う。

入っていない人は手元に書くだけで、送らない（第9章の12）。

#### 手元に残せる量

提出の控えは**200件まで**（`MAX_SUBMISSIONS`）。これを超えると古いものから落ちる。入らずに200問以上解いてから登録した人は、古い提出が運営の画面に出ない。節の状態は全部残るので、どこまで進んだかは分かる。

## 7. API

`/api/` の下。すべて JSON。ログインが要るものは Cookie のセッションで判定する。

| メソッド | 経路 | 用途 |
|---|---|---|
| POST | `/api/register` | 招待コードと表示名で登録。IDとパスワードを返す |
| POST | `/api/login` | 利用者IDとパスワードでログイン |
| POST | `/api/logout` | ログアウト |
| GET | `/api/me` | 自分の情報と進度をまとめて返す |
| POST | `/api/progress` | 節を開いた／終えた、滞在時間を送る |
| POST | `/api/submit` | 課題の提出（コード・合否・落ちたテスト・エラー型） |
| POST | `/api/answer` | 確認問題の回答 |
| GET | `/api/staff/roster` | 所属の全学生の進度一覧（運営以上） |
| GET | `/api/staff/stuck` | 詰まっている学生と箇所（運営以上） |
| GET | `/api/staff/user/:id` | 1人の詳細と提出コード（運営以上） |
| POST | `/api/staff/comment` | コメントを書く（運営以上） |
| POST | `/api/staff/cohort` | 招待コードの発行（運営以上。触る先は `invite_codes`。第5.2.1節） |
| POST | `/api/staff/user/:id/passcode` | パスワードの作り直し（運営以上。範囲と規則は第5.3節） |
| POST | `/api/admin/role` | ロールの変更（管理者のみ） |

進度の送信は**節を離れるときと30秒ごと**にまとめて送る。1操作ごとには送らない。

### 7.1 画面から呼ぶときの決まり（2026-09-14 追加）

- **POST には必ず `content-type: application/json` を付ける。** 付けずに POST すると Astro が「他所からのフォーム送信」とみなして 403 `Cross-site POST form submissions are forbidden` を返す。本文が空の `/api/logout` でも同じ
- Cookie は `HttpOnly` なので画面の JavaScript からは読めない。`fetch` は同じサイト宛てなら自動で付く
- `/api/me` は**ログインしていなくても 200 と `{ "user": null }`** を返す。401 は「設定が壊れている」ときにしか出ない。画面は `user` が null かどうかだけを見る
- 断りの応答は `{ error, field? }`。`field` は画面が置き場所を選ぶためだけのもの（第5.6節）
- パスワードは画面に `690 399` と3桁ずつ空けて出すので、**サーバは受け取ったパスワードから空白を落としてから照合する**。写したまま打った人を弾かないため

### 7.2 登録の口に上限を置く（2026-09-14 決定）

`MLAB-OPEN` は誰でも使える常設のコードなので、機械で叩けば口座をいくらでも作れる。1件につき D1 への書き込みが2回（`users` と `sessions`）発生し、無料枠は1日10万回。

**外部の所属にだけ上限を置く。1時間に10件、1日に50件。**超えたら 429 と「いまは登録できません。しばらくしてからもう一度お試しください。」を返す。あと何件作れるかは出さない（上限を測りながら叩く相手に教えないため）。

**内部の所属には置かない。** 勉強会で30人が一斉に登録する場面を止めるのがいちばん困る。内部のコードは配った相手しか知らないので、そもそも蛇口が開いていない。

数えるのは同じ所属の `users.created_at` だけである。**送信元のアドレスは記録しない**（第5.5節「集めるのは表示名だけ」）。新しい表も要らない。

この作りの弱点は、外部から叩かれている間は外部の人が登録できなくなること。1時間で自然に空くこと、内部の学習者は影響を受けないこと、運営が `users` を見れば起きていると分かることから、この規模では受け入れる。足りなくなったら Cloudflare 側の Rate Limiting を足す。

## 8. 運営の画面

`/staff/` の下。運営ロール以上でだけ開ける。

### 8.1 一覧

学生を行、章を列にした表。セルは**未着手 / 開いた / 済**の3状態を色で示す。行の末尾に最終アクセス日。

並び替えは「進度が遅い順」を既定にする。勉強会の前に、遅れている人から見るため。

### 8.2 詰まっているところ

次の条件のどれかに当てはまる学生と箇所を並べる。**この画面が運営の画面の主役**。

| 条件 | しきい値 |
|---|---|
| 同じ課題を繰り返し落としている | 5回以上落ちて未通過 |
| 同じ節に長くとどまっている | 想定所要時間の3倍以上 |
| 最後のアクセスから間が空いた | 10日以上 |

各行から、その学生の提出コードに1クリックで飛べる。

### 8.3 問いごとの正答率

課題と確認問題を、**正答率の低い順**に並べる。これは学生ではなく**教材を直すための画面**。分母が5人未満のものは灰色にする。

### 8.4 1人の詳細

進度、提出コードの履歴（新しい順）、確認問題の回答、コメントのやりとり。

提出コードは**そのまま表示する**。整形しない。書き方の癖と誤解を読むためなので、直したものを見せては意味がない。

### 8.5 コメントとやりとり

学習者が送った質問と、運営が書いた返事は、**その節の1本のやりとりとして時刻の順に並べる**（2026-09-15 追加）。質問だけ・返事だけを別々に見せると、何に対する返事かが分からなくなる。

| | 決めたこと |
|---|---|
| 置き場所 | 学習者側は右レールの「質問」。入っている人にだけ出る（第10.1節） |
| 並び | **古い順。** 会話なので上から下へ読む |
| 未読 | `comments.read_at` が空のものを数え、レールのボタンに件数を出す |
| 既読にする時機 | **学習者がやりとりを開いたとき。** 節を開いただけでは既読にしない |
| 書ける人 | 質問は学習者、返事は運営以上。**学習者どうしは見えない** |
| 消す | 作らない。書き直しも作らない。記録として残す |

## 10. 質問

学習者が詰まったその場で質問を送れるようにする。宿題中に詰まった人を、次の勉強会まで放置しないため。

### 10.1 学習者側

- 右レールの「質問」から送る。**入っている人にだけ出す（2026-09-14 決定）。** 送り先が自分のアカウントに紐づくので、入っていない人には置き場所がない。押せない欄を見せる意味もない
- **ボタンには役の名前を書かない。**「質問する」とだけ書く。学習者にとっては答える相手が誰かは関係がなく、答えるのは上級生のこともあれば卒業生のこともある（第5.4節）
- 送信時に、**いま開いている節のIDと、直前に提出したコード（あれば）を自動で添える**。学習者は状況を説明しなくてよい
- 本文は必須。空では送れない
- 送ったあとは、その節に自分の質問と返信が残る
- 返信が来たら、上部に件数が出る

### 10.2 運営側

- `/staff/questions` に未返信のものから並ぶ
- 各行に、質問・節・添付されたコード・その学生の進度が同じ画面で見える。別の画面に飛ばない
- 返信すると、第8.5節のコメントとして学生に届く

### 10.3 テーブル

```sql
CREATE TABLE questions (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     TEXT NOT NULL REFERENCES users(id),
  lesson_id   TEXT NOT NULL,
  exercise_id TEXT,
  code        TEXT,                    -- 直前の提出。無ければ NULL
  body        TEXT NOT NULL,
  answered_at INTEGER,
  created_at  INTEGER NOT NULL
);
```

API: `POST /api/question`（学習者）、`GET /api/thread`（学習者・自分のやりとり）、`GET /api/staff/questions`（運営以上）。返信は `POST /api/staff/comment` を使う。

## 11. 第0章「パソコンの操作」の範囲

レベル0で必修、レベル1で任意、レベル2では確認テストで飛ばせる。

### 11.1 扱うもの

| 項目 | 扱い方 |
|---|---|
| 全角と半角、日本語入力の切り替え | **この教材で最も事故が多い箇所。** `（` `”` `：` `＝` `１００` `，` の全角が実際に踏まれている。半角で入力する練習を、その場の入力欄でさせる |
| 記号の入力方法 | `"` `_` `#` `*` `[` `{` `|` `~` の位置と Shift の組み合わせ。**キーボードの配列は人によって違う**ので、図で教えるのではなく、入力欄に打たせて合っているか判定する |
| ファイルとフォルダ、拡張子 | 保存先が分かる、拡張子を表示する設定にする。第5部（自分の環境）で必須になる |
| コピーと貼り付け、選択 | `Ctrl+C` `Ctrl+V` `Ctrl+A`、ドラッグでの選択、行の選択 |
| 取り消し | `Ctrl+Z`。**書き間違えたコードを戻せると分かっているかどうかで、手の動きが変わる** |

### 11.2 扱わないもの

- 文章を書くこと自体（レポートで既にやっている）
- 機種やOSによって違う操作（特定のノートPC固有のキーなど）
- タッチタイピング

### 11.3 書き方

**説明より練習を主にする。** この章だけは、本文を短くして入力欄を多く置く。判定は入力された文字列を直接見る（半角になっているか、記号が合っているか）。Python の実行は使わない。

### 11.4 課題の型（第0章だけ）

第0章は Python を動かさない。既存の `<Exercise>` に **2つの `kind` を足す**。新しい部品は作らない。
進度の記録・採点の応答・模範解答の扱いは、Python の節とまったく同じ仕組みに乗せる。

```ts
kind: 'trace' | 'modify' | 'build' | 'type' | 'choose';

type Test =
  | { kind: 'stdout'; stdin?: string; expect?: string }
  | { kind: 'call'; fn: string; args: unknown[]; expect?: string }
  | { kind: 'text'; expect: string }            // 打った文字列そのものを見る
  | { kind: 'choice'; correct: number };        // 選んだ番号を見る
```

**`kind="type"`（打つ練習）**

- コード欄ではなく**1行の入力欄**を出す。CodeMirror も Pyodide も読み込まない
- 判定は `{ kind: 'text', expect }` との**完全一致**。前後の空白だけは落とす
- 模範解答の `.py` は置かない。`expect` がそのまま答えなので、合格するまで見せない
- **全角が混ざっていたら、不一致とだけ言わずに「全角が混ざっています」と出す。**
  この章の目的そのものなので、ここだけは専用の応答を持つ（第4.3節の例外）

**`kind="choose"`（選ぶ練習）**

- 選択肢を `<Exercise>` の子として `<li>` で並べる。判定は `{ kind: 'choice', correct }`
- 画面の操作のように機械が確かめられないものに使う（0.4 の拡張子の表示）
- **これは自己申告である。**選んだ番号が合っているかしか見ない。運営の画面では
  第8章の「詰まっているところ」に混ぜない

#### 実装で決めたこと（2026-09-12）

**`correct` は1から数える。**画面に出る番号と同じにする。2つ目の選択肢が答えなら `correct: 2`。
0から数えると、書き手が見ている画面の番号と書く値が1ずれる。ずれても検査は通ってしまい、
落ちるのは学習者の画面である。番号を合わせておけば、書き手が見たまま書ける。

**選択肢は問題文の最後の箇条書きにする。**`<Exercise>` が問題文を組んだあと、最後の `<ul>` を
問題文から抜き、番号付きのラジオボタンに組み替えて島に渡す。`check-lessons.mjs` も同じく
後ろから数えるので、`correct` が選択肢の数を超えていればビルドが落ちる。

**判定の形は型ごとに1件に固定する。**

| `kind` | `tests` | `starter` | 模範解答 `.py` |
|---|---|---|---|
| `type` | `{ kind: 'text', expect }` を1件 | 置かない | 置かない |
| `choose` | `{ kind: 'choice', correct }` を1件 | 置かない | 置かない |

`text` と `choice` は第0章の型でだけ使える。`trace` / `modify` / `build` に混ぜたら検査4で落ちる。

**全角の指摘の出し方。**「まだ通っていません」の下に「全角が混ざっています」を置き、続けて
**何文字目のどの文字が全角か、その半角の相手は何か**を1つずつ並べる。

- 拾うのは**半角の相手を持つ全角だけ**（`！`〜`～` の全角英数記号、全角の空白、`“ ” ‘ ’`）。
  ひらがなと漢字は拾わない。打つ見本に日本語が入ることがあるため
- `expect` に元から入っている文字は拾わない。書き手が意図して置いたものなので
- 同じ文字が何度も出てきたら、最初の1つだけ出す

**見本（`expect`）は不一致のときも出さない。**答えそのものだからである。代わりに
**何文字目から違うか**と、**学習者が打った文字**を出す。位置は答えを明かさずに直せる手がかりになる。

**`expect` と `correct` はブラウザに渡る。**第4.2節が模範解答を配らない理由は、答えを読めば
課題が成立しなくなるためだが、第0章の「打つ練習」は画面に見本が出ている課題である。
隠す相手がいない。「選ぶ練習」も自己申告なので、正解の番号を隠しても確かめたことにはならない。
どちらもサーバ側に判定を置かず、生成物に載せる。Python の節の `expect`（第4.2節）は
これまでどおり模範解答から作り、模範解答そのものは配らない。

### 11.5 第0章だけの例外

第0章（`chapter: 00-start`）は、次の規則から外れる。**ほかの章には一切適用しない。**

| 「組む」が1問以上（検査4） | `kind="type"` が1問以上に読み替える。0.4 だけは `kind="choose"` が1問以上 |
| `kind` は3種類（検査4） | `type` と `choose` を足した5種類。**ほかの章では3種類のまま** |

### 11.6 「やってみる」に課題を1問置く

**（2026-09-12 追加。4節とも「やってみる」が予告の文だけになっていたため）**

ふつうの章は「やってみる」に `<Run>` を置く。第0章は `<Run>` を置かないので、**そこに課題を1問置く**。
「下に入力欄が出ます」と予告するだけの文にしてはいけない。それでは読者が説明を読んでから打つことに
なり、第2章の「**説明より先に置く**」が崩れる。練習を主にすると決めた章で順序が逆になる。

- 0.1〜0.3 は `kind="type"` を1問
- 0.4 は `kind="choose"` を1問。**まだ設定を変えていない状態で、いま画面がどう見えているかを選ばせる**

この1問も、課題4〜7問のうちに数える。

**機械判定の書き方（2026-09-12）。**「組む」の読み替えは、`check-lessons.mjs` では
**`kind="type"` と `kind="choose"` を合わせて1問以上**として見る。節ごとにどちらが要るかは
機械では決められないため（0.4 だけが `choose`）。ここは書き手と査読が見る。

### 11.7 第0章の追加の規定（2026-09-12）

書き上がった4節を、パソコンが初めての人と、パソコンは使えるがプログラミングが初めての人の
2つの視点で読ませた結果から決めた。第0章は5節に組み直す（`30-python-curriculum.md` 第3.2節）。

**「よくある間違い」を第0章から外す。**

`<Mistake>` は壊れたコードと実際のエラーメッセージを見せる要素である。パソコンの操作を習いに
来た人に `SyntaxError: invalid character '“' (U+201C)` を見せる理由がない。第0章の要素の順序は
**困る例 → やってみる → 説明 → 課題 → つながり** になる。検査3は第0章では見ない。

**課題は1問ずつ出す。**

第0章は打つ練習が1節に5〜6問続く。縦に全部並べると、どこまでやったかが分からず、終わりも見えない。
**1問に通ると、その場が次の問題に入れ替わる。**いま何問目かと全部で何問かを、その場に出す。

- 通った問題は消える。戻る道は作らない（第0章の練習は、戻って読み返す価値が薄い）
- 全部通ったら「この節の練習は終わりです」を出す
- **この形は第0章だけ。**Python の章は例題・練習問題・演習問題で段が違い、前の問題のコードを
  見ながら次を解くことがあるので、縦に並べたままにする

**貼り付けを使ったかどうかを見る（0.4 だけ）。**

`kind="type"` に `requirePaste` を足す。入力欄で貼り付けが起きたかを記録し、起きていなければ
通さない。応答は「手で打っても同じ文字になりますが、この問題はコピーと貼り付けを使って解いて
ください」とする。**貼り付けの中身は見ない。**起きたかどうかだけを見る。

当初の0.3は、課題がどれも最終的な文字列の一致だけを見ていたため、`Ctrl+C` を一度も使わずに
全問通った。節の題が約束した技能を何も検証していなかった。

**キーボードの図（0.3 だけ）。**

`~` `|` `{` `[` のような、日常で使わず探しにくい記号に限って、キーの位置の図を `<Level0>` の中に置く。

- **JIS配列の一例であることを必ず明記する。**「あなたのキーボードと違う場合があります」
- 日常で触れる記号（`( ) " : = ,`）には置かない
- 本文には置かない。詰まったときの逃げ道として補足の中に置く

第11.1節の「図で教えるのではなく、入力欄に打たせて判定する」は変えない。図は判定の代わりでは
なく、詰まったときの手がかりである。

#### 実装で決めたこと（2026-09-13）

**束にするのは「続けて並んだ課題」である。**本文には `<Exercise>` が縦に並んだまま書かれる。
書き手は何も書き足さない。包む側（`src/lesson/exercise-queue.ts`）が、隣り合って並んだ課題を
1つの束にし、**2問以上の束だけ**を1問ずつに切り替える。

これで第11.6節の「やってみる」の1問は自動的に外れる。前後に本文が入るので1つきりの束になり、
入れ替える相手がいない。読んでから説明に進む1問なので、そこは縦に並べたままでよい。

**何問目かの表示は「6問中 4問目」。**帯の下、問題文の上に置く。札は増やさない（第10.6節）ので、
コードのキャプションと同じ組み（Zen Old Mincho 13px・字間 .14em・`#5d564a`）にした。

**通ったら、その場で入れ替える。**合格の応答を出したまま止めない。何が起きたかは
**問題が入れ替わったことと、何問目かの表示が1つ進むこと**が示す。戻る道は作らない。

**終わりは罫の下に1行置く。**「この節の練習は終わりです」。地色も札も足さない。

**JS が動く前は CSS で伏せる。**第0章の節だけ `.lesson-body` に `data-exq` が付く。

### 11.8 第0章の課題は手を動かしてから答える

**（2026-09-14 追加）**

第0章はパソコンの操作を扱う。課題も、**学習者が自分のパソコンで何かをしてから答えるもの**を軸にする。用語を思い出すだけで答えられる問いは、操作を1度も起こさない。

「選ぶ」の型でこれを作るには、問題文で操作を指示し、**その操作をしないと分からないもの**を選ばせる。

- よい: 「エクスプローラーでファイルを1つ見てください。いま、ファイル名の末尾に何が見えますか」→ 実際に見ないと答えられない
- 悪い: 「拡張子の説明として、正しいものはどれですか」→ 本文を思い出せば答えられる

各節に、手を動かしてから答える問いを**最低1問**置く。用語の言い換えを選ばせる問いの上限は `10-lesson-and-writing.md` 第3.7節（1節に1問まで）。

**この規定は機械では検査できない。** 検査14が見ているのは「◯◯の説明として」という**言い回し**であって、「操作しないと答えられないか」という**性質**ではない。その2つは別物である。

実際に取り違えた。第0.5節をこの規定に沿って書き直させたところ、検査14は通ったが、出来上がった3問はこうだった。

| 問い | 操作しなくても答えられる理由 |
|---|---|
| 左の列に並んでいるのはどれですか（デスクトップ / 電卓 / メール一覧 / 再生リスト） | 誤答が場違いすぎて、見なくても消去法で決まる |
| `sample` という名前のフォルダを作り、その名前を打ってください | **答えが問題文に書いてある** |
| 作ったフォルダの中に何が入っていますか（… / 何も入っていない / …） | いま作ったばかりの箱なので、考えれば分かる |

だから人が読んで次の1点を確かめる。**問題文と選択肢だけを見て、パソコンに触らずに答えが決まらないか。** 決まるならその問いは操作を起こさない。

作り替えたあとの形が見本になる。`sample` の中に `naka` を作らせ、`naka` を開いたときに上の帯へ何と何が並ぶかを選ばせる。この答えはどこにも書いていないし、入れ子にして開くまで画面に出ない。

**2026-09-24 に改めた（第0章の見直し）。**利用者の指摘:「画面に何があるかと聞かれても意味がない」「理解の確認なら確認問題、練習しないと分からないものなら練習問題」。第0章は第2.0節（型に当てはめて書かない）が決まる前に書かれ、枠を埋めるための問いが残っていた。

- **画面によって答えが変わる問いは置かない**（タスクバーのアイコン、左の列の項目、設定しだいで見えるもの）
- 操作は、**個人の情報を消した画面の写真**（`public/images/start/`）を見ながら行わせる。答えになる写真は載せない
- 問いは、理解を確かめるもの（確認問題）か、練習しないと身につかないもの（練習問題）だけにする。32問を13問にした

### 12.1 通ったときに箱を消さない

いまは束の最後の1問に通ると、箱が消えて「この節の練習は終わりです」という文だけが残る。

- **箱はそのまま残す。**上を半透明で覆い、達成の印（チェックマーク）を重ねる
- 1問ごとに通ったときも同じ。覆いを出してから次の問題に入れ替える
- 束を全部通したら、最後の問題の箱を覆ったまま残す

印の色は**緑**にする。**この教材で初めて使う色である。**紙の地色と朱・藍・琥珀・墨の上で
浮かない深さにする。第10.9節の色の表に加える。

#### 通ったときの見せ方（2026-09-13 決定。案D）

3案（箱全体を覆いっぱなし・一瞬だけ覆う・はじめから帯の外だけ覆う）を画面で見比べて決めた。
決まったのは次の2段である。

1. **通った瞬間**は、箱の枠の内側いっぱいを紙色 `rgba(246, 242, 233, 0.62)` で覆う。帯も一緒に沈める。
   チェックマークは箱の中央に大きく置く
2. **約1秒後**（次の問題に入れ替わるのと同じ間）に、覆いが**帯の外だけ**に縮み、濃さが `0.35` に下がる。
   **帯の色（藍・朱・無彩）は戻る。**チェックマークは動かさない。大きさも位置もそのままである

移り変わりは 0.45秒。**覆う瞬間だけは待たせない。**箱の中身と帯が同じ瞬間に沈まないと、ひと続きに見えない。
滑らかにするのは落ち着いていく側だけでよい。

**進度から戻したときは、はじめから2の状態で出す。**ページを開き直すたびに覆いが光ってはいけない。

##### 実装で決めたこと（2026-09-14）

**1問きりも束として持つ。**`exercise-queue.ts` は隣り合う `<Exercise>` を束にし、2問以上の束だけを

### 12.2 キーボードから手を離さずに採点する

打ち終わってから採点のためにマウスへ手を移すのが煩わしい。**`Ctrl` ＋ `Enter` で採点できる**
ようにする。打つ欄・コード欄のどちらでも効く。

- 第0.1節（この教材の使い方）で、この操作を教える
- 押せることが画面から分かるようにする。採点ボタンの近くに小さく出す
- **ボタンは残す。**キーボードの操作は足すだけで、置き換えない

### 12.3 答えが決まっている課題は自動で採点する

選ぶ課題と打つ課題は、**答えが1つに決まっている**。押させる理由が薄い。

- 正しい状態になってから **0.5秒待って**、自動で採点する
- 0.5秒待つのは、打っている途中でたまたま一致したときに早とちりしないため
- **採点ボタンは残す。**自分で押したい人のために残す
- **Python の課題（`trace` `modify` `build`）は自動採点しない。**動かしてみないと合否が
  決まらず、走らせるのに時間がかかるため。打ち終わったかどうかを機械が決められない
- `requirePaste` の課題は、貼り付けが起きたときだけ自動採点の対象にする

**選ぶ課題に採点ボタンを置かない（2026-09-14）。**選んだ時点で答えたのと同じである。
押させる手数が1つ増えるだけで、選び直しは選択肢を選び直せばよい。打つ課題はボタンを残す
（打っている途中は答えが定まらないため）。

#### 実装で決めたこと（2026-09-14）

**選ぶ課題は、選んだらどれでも採点する。**打つ課題の自動採点は「正しい状態になってから」0.5秒待つ
形で、合っていないうちはボタンが受け持っていた。ボタンを消した選ぶ課題で同じ形にすると、
**違う番号を選んでも何も返らない**。選んだ時点で答えたのと同じだと決めた以上、合っていない選択も
採点して「選んだものは違います」を返す。落ちた回数も今までどおり数え、ヒントの出方は変わらない。

**0.5秒の待ちはそのまま置く。**押し間違いを選び直す猶予になる。選び直せば、そのつど採点し直す。

**同じ答えを採点し続けない。**採点が終わると採点中の印が下りるので、「選んだら採点する」だけでは
同じ番号をいつまでも採点し直してしまう。一度自動で採点した番号を覚えておき、選び直されるまで
動かさない。

**採点の欄そのものを出さない。**ボタンだけを消すと、空の欄の分だけ箱の底が空く。選ぶ課題では
`.kit-ex__bar` を丸ごと出さない。選択肢の並びの下は `.kit-ex__in` の余白だけになる。

**`Ctrl` ＋ `Enter` は選ぶ課題でも効いたままにする。**注記は消す（第12.2節の「押せることが画面から
分かるように」は、押すものが無ければ書きようがない）。キーの受け口は打つ欄・選択肢・コード欄を包む
器に付いているので、外す理由がない。

第0章は、パソコンがほぼ初めての人に合わせてある。**プログラミングをかじったことがある人に

- `00-overview.md` 第2.3節のレベル（0・1・2）の入り口を、この結果で決める

### 13.6 活動の記録

**取り組んだ時間は「活動した分」を数えて推定する。**節の画面を開いたままの放置を数えないためである

読んでいて手が止まる時間を120秒まで許す。

```sql
CREATE TABLE activity_minutes (
  user_id   TEXT    NOT NULL REFERENCES users(id),
  minute    INTEGER NOT NULL,          -- その分の始まり（ミリ秒、60000 の倍数）
  lesson_id TEXT    NOT NULL DEFAULT '', -- 節の id。メンバーの画面なら 'home'

);
```

- 画面側: 教材の各節と `/learn/home/` で動かす。15秒ごとに「いま活動しているか」を見て、していればその分（`Math.floor(Date.now() / 60000) * 60000`）を手元の集合に足す。**いまある30秒ごとの送信と、`pagehide` / 裏に回ったとき**に一緒に送る
- 送る口: `POST /api/activity`、本文は `{ minutes: [{ minute, lessonId }] }`。入っていない人は何も送らない（口も 401 を返す）。1回200件まで。`minute` が 60000 の倍数でない・いまより2分以上先・7日より前のものは黙って捨てる。`INSERT OR IGNORE`
- **取り組んだ時間 = 活動した分の行数。**同じ分に2つのタブで活動しても1分（主キーで重ならない）
- 書き込み量の目安: 1人が1時間取り組むと60行。D1 の無料枠（1日10万行）に対して十分小さい

### 13.7 活動を見る画面（運営）

`/staff/activity/`。運営の画面の上のリンク列に「活動」を足す。見える範囲は第5.4節のとおり。

1. **一覧**: メンバーごとに1行。表示名・最後に活動した日時・**今週**（月曜0時〜、日本時間）の取り組んだ時間・先週・直近4週の合計・済んだ節の数。時間は「1時間10分」の形
2. **時間帯の表**: 直近4週の活動した分を、曜日（月〜日）×時（0〜23時、日本時間）の7×24のマスに数える。濃さは既存のインクの色の不透明度だけで表す（新しい色を足さない）。上に人を選ぶ欄（既定は全員の合計）。マスに `title` で「火曜 21時: 34分」
3. **最近の出来事**: 新しい順に50件。種類は3つ: 節を済ませた（`progress.done_at`）・課題を提出した（`submissions`、通った／落ちた）・質問した（`questions`）。誰が・いつ（日本時間）・どの節（番号と題）

### 14.4 表示名とパスワードでログインする（2026-09-24 決定）

利用者の指摘:「利用者IDもパスワードのようになっている」。利用者自身が、表示名でログインしようとして入れなかった。
**ログインは表示名とパスワードで行う。**第5.2節・第5.3節の「利用者ID」を画面から外す。

- ログインの小窓の欄は「表示名」と「パスワード」。`u_` で始まる入力（大文字小文字を問わない）は、**これまでどおり利用者IDとして受ける**。IDを控えている人を困らせないため
- **表示名は重複させない。**比べるときは、前後の空白を落とし、NFKC で正規化し（全角の英数字を半角に）、大文字小文字を区別しない。登録で重なったら、欄の下に「この表示名はすでに使われています。別の表示名にしてください。」
- 保存する表示名は、NFKC で正規化して前後の空白を落としたもの。ログインの入力も同じ処理をしてから引く
- `migrations/0006_display_name_unique.sql`: `CREATE UNIQUE INDEX users_display_name ON users (display_name COLLATE NOCASE);`
- 失敗の数え方と待ち時間は第5.3節のまま（利用者ごと）。表示名が無いときとパスワードが違うときは同じ文面「表示名かパスワードが違います」
- 登録直後の「控える」段は、**表示名とパスワード**を見せる（利用者IDは見せない）。「紙に書き写してください」はそのまま
- 右上のメニューに利用者IDは出さない（第14.1節から外した）
- **弱くなる点（承知のうえ）**: 表示名は推測できるので、知っている人がわざとパスワードを外し続けると、その人を最大1時間待たせられる。利用者IDは推測できなかったのでこれが起きなかった。5人程度の身内の場なので、いまは受け入れる

### 14.5 ログインする前の進度は、尋ねずに捨てる（2026-09-24 決定）

第6.1節「入ったときに手元の進度をどうするか」と第6.2節の表の `owner` が `null` の行を改める。

利用者の判断:

- 尋ねる段は、ほとんどの場合ただ邪魔になる
- ログインする前の記録が残らなくても、本人が学んだことに変わりはない。照合を作るのは実装を重くするだけ

**ログインした直後、`owner` が `null` なら、尋ねず、比べず、手元の進度を捨てる。**そのうえで `owner` をログインした人にし、サーバの記録を手元に引き写す。

- 小窓の4つ目の段（引き継ぎ）は出さなくなる。**段そのものと、段を出すための処理は取り除く**
- `owner` が入った人と同じとき、別の人のときの扱いは第6.2節の表のまま

### 14.6 押せるものは、マウスを乗せたら見た目を変える（2026-09-24 決定）

利用者の指摘:「ボタンの類は、マウスを乗せたら何かしら表示が変わる仕組みにしてほしい」。

### 14.7 第0章の課題を行き来できるようにする（2026-09-24 決定）

## 15. 練習編と、組み合わせて使う力（2026-09-24 決定）

- 色は既存のトークンだけ。朱と藍の組み合わせは色覚の違いがあっても見分けられることを確かめてある（ΔE 11.9）。接線は破線にし、色だけに頼らない

### 16.2 動かし方

- **既定では自動でくり返す。** h を 2 から 0.01 まで対数の刻みで約6秒かけて小さくし、1秒止まって、また 2 に戻る
- **止める／動かすのボタン**を置く（5秒を超えて動き続けるものには止める手段が要る）。ボタンは文字にせず、**止めるは朱の四角、動かすは墨の三角**で示す（2026-09-25 利用者の指定。動く図すべてで同じ）。読み上げの名前は aria-label で「止める」「動かす」。つまみ（`<input type="range">`）も置き、触ったら自動は止まり手で動かせる
- `prefers-reduced-motion: reduce` なら、**最初から止めておく**（h = 2 の図と、止まっていることが分かる表示）
- 画面の外にあるときは動かさない（見えている間だけ動く。見えない間に CPU を使わない）

### 16.3 部品

`src/components/lesson/Secant.astro`。本文（MDX）からは次のように使う。

```mdx
<Secant fn="x**2" x0={3} xmin={0} xmax={5.4} ymin={0} ymax={28} caption="x = 3 での傾き" />
```

- `fn` は決まった式だけを受ける（`x**2`、`x**3`、`x**2 - 4*x + 5` など、第10章で使うものを部品の中の表に並べる）。**本文から任意の式を評価しない**（`eval` を使わない）
- 接線の傾きは、部品の中の表に式ごとの導関数を持たせて描く
- 知らない `fn` を渡されたら、ビルドで止める（`<Keys>` `<Figure>` と同じく、間違いは検査で止まる形にする）
- 図は SVG。尺度は1つで、線・目盛り・名前をその尺度から置く（手で座標を書かない）
- 狭い画面では、図は本文の幅に縮む。表は図の下

### 16.4 実装で決めたこと（2026-09-24）

- 式の表と尺度は `src/lesson/ui/secant.ts` に1つだけ置き、ビルド時に図を組む側とブラウザで動かす側の両方が読む。使える式は `x**2` / `x**3` / `x**2 - 4*x + 5`。足すときは導関数と一緒にこの表へ1行足す
- ビルドで止めるもの: 知らない `fn`、数でない値（`x0="3"`）、`xmin >= xmax` などの逆転、`x0 < xmin` または `x0 + 2 > xmax`（h = 2 の右の点が範囲の外）、`x0` と `x0 + 2` での値が `ymin`〜`ymax` の外、曲線の名前を線に重ねずに置ける場所が無い
- 曲線の名前の位置: 曲線に沿って候補を並べ、曲線・接線・h を 2〜0.01 で動かしたときの2点を結ぶ直線のどれにも触れないものの中から、接線と2点を結ぶ直線からいちばん離れたものを選ぶ
- 表の傾きは、通った瞬間の h ではなく決まった h（2, 1, 0.5, 0.1, 0.01）で計算し、小数4桁にそろえる（Python で出す表と同じ値になる）。行は h の大きい順に並べ、くり返しても増やさない。つまみで決まった h を通ったときも積む
- つまみは 0〜100 の101段（対数）。矢印キー1回で h が約5%変わる
- 見えている間だけ動かす: IntersectionObserver が一度でも知らせてきたらそれに従い、一度も来ない環境（描画していない枠）ではタブが見えているか（`document.visibilityState`）だけで決める。1コマは requestAnimationFrame と 50ms の時計の先に来たほうで進める（描画していない枠では rAF が一度も来ないため）
- h の表示は `<output>` にしない。`<output>` は読み上げの対象（status）になり、毎コマ読み上げられるため
- 狭い画面（560px 以下）では SVG の中の字だけを大きくする（目盛り 13→20、曲線の名前 14→21、viewBox の単位）。曲線の名前の置き場所は大きいほうの字で見積もる
- 枠と題は `<Figure>` と同じ（`.kit-fig` / `.kit-fig__cap` / `.kit-fig__in`）。目盛りの格子は `--l-lv2`、0 の線は `--l-rule`
- 本文の検査（`scripts/parse-lesson.mjs`）の部品の一覧に `Secant` を足した。足さないと、タグがそのまま地の文として数えられる

## 18. 用語の検索と右の欄（2026-09-25 決定）

利用者の提案「質問はたぶん使われない。用語集と合わせて検索にしたい。コードを書いていて、array ってどう使うんだっけとなったときに引ける。右側が余っているので使いたい」。試作の**案B（右の欄に常設）**に決めた。

### 18.2 欄の中身（上から）

1. **検索欄。**見出しの言葉は「用語を検索」。欄に入ると、薄い字で例を1つ出す（`例: print`）。例は、いま見ている節までに習った用語から毎回ランダムに選ぶ。どんな言葉で引けばよいかが分かるように（利用者の提案）。`/` キーでも欄に入る

5. いちばん下に「探しても分からないときは この節について質問する」（ログインしている人だけ。今の質問の小窓を開く）と、「用語集の一覧」へのリンク

左の欄にあった「用語集」と「質問」の2つは、この欄に移して左からは外す。第0.1節の「画面の左側には…用語集があります」も合わせて直す

### 18.3 引けるもの

- **用語**: 用語集の語（`design/spec/glossary.md`）。札には、語・英語・定義・**使い方の例**・「第N章M節 題 を開く →」
- **書き方**: Python の書き方の台帳（`scripts/python-tools.mjs`）にあって用語集に無いもの（`**`、`//`、`.T`、`@` など）。札の中身は用語と同じ
- **節**: 節の題。札には題と、その節で使う言葉と、「開く →」
- 候補と札に付ける種類の名前は「用語」「書き方」「節」の3つ。**「道具」とは呼ばない**（利用者の指摘。プログラミングでは見かけない言い方）
- **使い方の例**は、その語を習う節の「やってみる」にある最初の `<Run>` のコードと出力をそのまま使う。書き方の台帳の語は、その書き方に当たる最初の `<Run>`。例を別に書き起こさない（本文と食い違うため）

- 引く表はビルドのときに作る（`src/generated/`）。ページの中で表を組み立てない

### 18.4 言葉

- 「道具」を学習者に見える文に使わない。「ここまでに習ったこと」「書き方」など、指しているものの名前で書く（`scripts/lesson-rules.mjs` の BANNED で止める）

## 20. 教材の公開と、運営が確かめるためのメモ（2026-09-25 決定）
