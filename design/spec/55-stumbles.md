# 仕様 55: いまどの問題にいるか、と、つまずきの記録（2026-10-02 決定）

`20-platform.md` 第8章（運営の画面）・第13.6節（活動した分）、`53-ml-intro.md` 第11節（みんなの進み具合）に足す。食い違う所は、この文書を先にする。

## 1. なぜ作るか

代表の指摘（2026-10-02）。

- 集まりの最中、**メンバーがいまどの問題に取り組んでいるのか**が分かりにくい。問題1にいるのか、その次なのか。それさえ分かれば、あとは見に行ける
- メンバーが詰まっている所・何度も落ちている所とその原因、節を読むのに時間がかかりすぎていないか、を知りたい。**課題で落ちたあとに節を読み直しに来ている**なら、記録する価値がある（ただアクセスが多いだけなら、書き方を確かめに来ているだけなので放っておく）
- 集めた記録をもとに、教材の書き方や順番を見直したい。「分からない所を報告して」と言っても、誰も報告してくれない

いまある記録で分かること: 提出（コード・通ったか・落ちたテスト・エラーの種類）、活動した分（どのページにいたか）。**足りないのは「どの課題にいたか」**（提出する前は、どの課題に取り組んでいるかが分からない）。

## 2. 決まったこと（代表が選んだ案）

1. **いま**: 「みんなの進み具合」の表の「いま」の欄に、提出する前でも、取り組んでいる課題を出す。表の形は変えない
2. **つまずきの記録**: 運営の画面に新しいページ。課題ごとの表と節ごとの表、期間の切り替え、書き出しのボタン
3. **書き出し**: 名前ではなく利用者の id（`u_XXXXXX`）で書き出す

## 3. 記録するもの（ここだけデータベースを変える）

### 3.1 migration `0015_activity_exercise.sql`

```sql
ALTER TABLE activity_minutes ADD COLUMN exercise_id TEXT NOT NULL DEFAULT '';
```

活動した分の1行に、その分に取り組んでいた課題の id を添える。課題に取り組んでいない分（本文を読んでいる）は空のまま。**本番への適用は代表が行う。適用してから push する**（適用の前に新しいコードが動くと `/api/activity` が落ちる）。

### 3.2 画面の側: 「取り組んでいる課題」の決め方

`src/lesson/activity.ts` の `trackActivity` に足す。

- **取り組んでいる課題** = その人が最後に触った課題の箱（課題の箱の中での `pointerdown` `keydown` `input` `focusin`）。課題の箱は、課題の id を持つ要素（`ExerciseBox` の根。id を `data-` 属性で読めなければ足す）
- 触った課題が画面から完全に外れたら（箱が1ピクセルも見えていない）、取り組んでいる課題は「無し」に戻す（本文を読みに戻った）。もう一度触るまで無しのまま
- 15秒ごとの「いま活動しているか」の確かめで、その分の行に、そのときの取り組んでいる課題を入れる（同じ分の中で変わったら、あとのもので上書き）
- 取り組んでいる課題が**変わったとき**（無し → 課題、課題 → 別の課題）は、その分を手元に足して、すぐ送る（2秒のあいだにまとめる）。集まりの最中に「いま」が遅れないようにするため。入力が無いのに送ることは無い（変わるのは触ったときだけ。無しに戻るのはスクロールしたときで、どちらも入力）
- 活動した分を数える画面を増やす: いまの節・メンバーの画面に加えて、**今週の演習の回のページ**（`lessonId` に今週の演習の id）と**練習問題集の話題のページ**（話題の id）。送る時機は、節の画面と同じ（30秒ごと・画面を離れるとき・裏に回ったとき）。これらのページに進度の送信が無ければ、活動した分だけを同じ時機で送る

### 3.3 口（`/api/activity`）

- 本文の各行に `exerciseId`（文字列。無くてよい。80字で切る）を受ける
- `INSERT OR IGNORE` を、同じ分の行があれば `lesson_id` と `exercise_id` を上書きする形に変える（`ON CONFLICT(user_id, mode, minute) DO UPDATE`）。行数（= 取り組んだ時間）は変わらない
- ほかの決まり（捨てる条件・上限・401）は変えない

### 3.4 いまある集計への影響を確かめる

`activity_minutes.lesson_id` に、今週の演習の id と練習問題集の話題の id が入るようになる。`lesson_id` を読んでいる所（`src/server/staff-data.ts` の「長くとどまっている」、`src/server/activity.ts`、`src/server/live-progress.ts`、`src/server/questions.ts`、`src/server/lessons-publish.ts`）が、節でない id を黙って読み飛ばすことを確かめる。取り組んだ時間の合計（行数）には入る（今週の演習・練習問題集に取り組んだ時間も、取り組んだ時間である）。

## 4. 「いま」の欄（`src/server/live-progress.ts`）

- 1人につき、いちばん新しい提出と、いちばん新しい活動した分を比べる所はそのまま
- 活動した分のほうが新しく、その行に `exercise_id` があるとき: その課題がこのページの列にあれば列の札（「練習2」）、ほかのページの課題ならそのページの呼び名（いまと同じ）
- `exercise_id` が空のとき: いまと同じ（「このページ」など）
- 見た目は何も変えない（欄の中の言葉が変わるだけ）

## 5. つまずきの記録（`/staff/stumbles/`）

運営の画面の並び（詰まっているところ・質問・集まり・今週の演習・活動・教材の公開）の「活動」の次に「つまずきの記録」を足す。見える範囲は、ほかの運営の画面と同じ（`visibleUsers`、メンバーだけ、`mode = 'learner'` だけ）。見た目は `staff.css` のいまの表・見出し・切り替えをそのまま使う。新しい色や形を足さない。

### 5.1 期間

ページの上に切り替え（リンク。`?days=7|28|all`）: 「この7日」「この4週」「全部」。初めは「この4週」。提出は `created_at`、活動した分は `minute` で絞る。

### 5.2 課題ごとの表

期間の中に提出が1つでもあった課題を、1行ずつ。**並びは、落ちた回数（中央）の多い順**、同じなら通していない人の多い順。

| 列 | 中身 |
|---|---|
| 課題 | 課題の呼び方（`exerciseLabel`。「3.2 練習1」「今週の演習 10/6 問3」）。そのページへのリンク |
| 出した人 | 1回でも提出した人の数 |
| 通した人 | 通した人の数 |
| 落ちた回数（中央） | 出した人ごとの「通すまでに落ちた回数」（通していない人は、落ちた回数ぜんぶ）の中央の値 |
| かかった分（中央） | 出した人ごとの、その課題に取り組んでいた分の数（`activity_minutes.exercise_id`）の中央の値。記録が無ければ「–」（この仕様より前の記録には無い） |
| 多い落ち方 | 落ちた提出を、落ち方ごとに数えて多い順に2つまで。落ち方 = エラーの種類があればそれ（「NameError」）、無ければ「テストn で不一致」。「テスト2 で不一致 ×7、NameError ×3」 |

人が1人しか出していない課題も出す（メンバーは5人）。

### 5.3 節ごとの表

期間の中に活動した分が1つでもあった節（教材の節だけ。今週の演習・練習問題集・メンバーの画面は入れない）を、1行ずつ。**並びは、「落ちたあとに読み直された回数」の多い順**、同じなら「かかった分（中央）÷ 目安」の大きい順。

| 列 | 中身 |
|---|---|
| 節 | 節の番号と題。節へのリンク |
| 読んだ人 | 期間の中に、その節で活動した分が1つでもある人の数 |
| かかった分（中央） | 人ごとの、その節で活動した分の数の中央の値 |
| 目安 | 節の想定所要時間（分） |
| 落ちたあとに読み直された回数 | 下の決め方で数えた数。0 は「–」 |
| どの課題のあとか | 読み直しのきっかけになった課題を、多い順に3つまで（「今週の演習 10/6 問3 ×2」） |

**落ちたあとに読み直した、の決め方**

ある人がある課題 E を落とした（提出が不合格）。その時刻 t から、次のどちらか早いほうまでの間に、**E が載っているページとは別の節 L** で活動した分が1つでもあれば、「E のあとに L を読み直した」を1回と数える。

- 区切り: その人が E を通した時刻。通していなければ t から24時間
- 同じ人・同じ E・同じ L は、何度行き来しても1回
- E と同じページの中で本文に戻ったことは、数えない（区別できない）。節の中の課題は、**ほかの節**へ戻ったときだけ数える
- E が教材の節の課題のときは、その節より**前の節**だけを数える。通さないまま先の節へ進んだのは、読み直しではない。今週の演習・練習問題集の課題は、どの節でも数える
- 落としていない人が節を何度開いても、数えない（代表の指示: アクセスが多いだけなら放っておく）

### 5.4 書き出し

ページの上に「書き出す（JSON）」。`GET /api/staff/stumbles-export?days=…` が JSON を返し、ブラウザがファイルとして保存する（`Content-Disposition: attachment; filename="stumbles-YYYY-MM-DD.json"`）。運営・管理者だけ。見える範囲は画面と同じ。

**名前（表示名）は入れない。利用者の id だけ。**

```json
{
  "exportedAt": 1790000000000,
  "days": 28,
  "exercises": [
    {
      "exerciseId": "…", "label": "3.2 練習1", "page": "python-03-else",
      "people": [
        { "user": "u_7QK3M9", "passed": true, "failsBeforePass": 3, "minutes": 12,
          "attempts": [ { "at": 1790000000000, "passed": false, "failedTest": 2, "errorType": "", "code": "…" } ] }
      ]
    }
  ],
  "sections": [
    {
      "lessonId": "python-03-else", "label": "3.2 …", "estimateMinutes": 15,
      "people": [ { "user": "u_7QK3M9", "minutes": 31, "rereadAfterFail": ["weekly-2026-10-06-3"] } ]
    }
  ]
}
```

- `attempts` は古い順。1人・1課題につき新しいほうから20件まで。`code` は1件 4000 字で切る
- 画面の表は、この同じ材料から作る（数え方を2か所に書かない。`src/server/stumbles.ts` に1つ）

## 6. 変えないもの

- 「詰まっているところ」（`/staff/`）の出し方としきい値
- メンバーの画面に見えるもの（何も増えない）
- タイタニックのテスト用データの答えの扱い

## 7. 確かめること

- 数え方（中央の値、落ちた回数、落ちたあとに読み直した、期間）は、`src/server/stumbles.ts` の中の、データベースを読まない関数に分け、手で作った行を渡して確かめる（`node --test` か、いまのテストの置き方に合わせる）。確かめる場合: 通した人と通していない人、同じ人が同じ節へ2度戻る、通したあとに戻る（数えない）、24時間を過ぎて戻る（数えない）、同じページの課題（数えない）
- `npm run build` が通る
- 手元のデータベースに migration を当てて（`wrangler d1 migrations apply --local`。手元だけ）、`/api/activity` に `exerciseId` つきの行を送って入ること、同じ分を送り直して上書きされること
- 本番のデータベースには触らない
