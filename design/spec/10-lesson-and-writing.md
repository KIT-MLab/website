# 教材仕様 10: 節の型と執筆規約

この文書は「分かりやすい」を、書き手の感覚ではなく**判定できる条件**に置き換えたもの。
節を1つ書いたら、末尾の第8章のチェックリストにかける。1つでも×があればその節は不合格で、直すまで採用しない。

この規約は、レビューする人・執筆するサブエージェントの双方が従う。

---

## 1. なぜ規約が要るか

過去の失敗の形はいつも同じだった。「分かりやすくして」という指示が、**文章をこねる方向**に出る。言い換えを増やし、比喩を足し、抽象度を上げる。結果として字数だけ増えて、読者は何をすればいいか分からないままになる。

分かりやすさは文章の綾ではなく、**順序と検証**で作る。何のためにやるかを先に出す。動くものを先に見せる。自分で決める課題を置く。合っているかを機械が判定する。この4つが揃っていれば、文章が多少ぶっきらぼうでも学習は進む。逆に、この4つがなければ、どれだけ丁寧な文章でも進まない。

---

## 2. 節の構造

1つの節は、次の要素をこの順で持つ。順序を入れ替えてはいけない。

| # | 要素 | 必須 | 分量 | 規定 |
|---|---|---|---|---|
| 1 | 困る例 | 必須 | 50〜150字 | この節の道具がないと何ができないかを、具体的な場面で書く。「便利です」ではなく、できない状態を示す |
| 2 | やってみる | 必須 | コード2〜10行 | その場で実行できるコード。実行結果も併記する。**説明より先に置く** |
| 3 | 説明 | 必須 | 300〜600字 | 名前と規則。コードの各部分が何をしているかを、コードの行に対応づけて書く |
| 4 | よくある間違い | 必須 | 1〜3個 | 実際に出るエラーメッセージをそのまま載せ、原因と直し方を書く |
| 5 | 課題 | 必須 | 4〜7問 | 第3章の3段階に従う |
| 6 | つながり | 任意 | 1〜2文 | 次の節、または後の部で回収する話題への言及 |

### 2.1 「困る例」の書き方

**悪い例**（機能の紹介から始まっている）:

> 変数を使うと、値を保存しておくことができます。

**良い例**（できない状態から始まっている）:

> 消費税込みの値段を3つ計算するとします。`108`、`216`、`324` と書けば答えは出ますが、税率が10%に変わったら3か所を直すことになります。10か所あれば10か所です。

### 2.2 「やってみる」の書き方

- 実行できる完全なコードを置く。断片（`...` を含むもの）は置かない
- 実行結果を必ず併記する
- ここでは説明しない。読者は「よく分からないが動いた」で通過してよい

### 2.3 「説明」の書き方

- コードの行番号か、コード中の記号を引用して対応づける
- 新しく名前を付ける概念は**1節に1つまで**。2つ目が必要になったら節を割る
  - その1つに付随する語は含めてよい（例: 「関数」の節で「引数」「返り値」を出すのは可）
- 規則を書いたら、その規則が破られた例を1つ置く（第4要素の「よくある間違い」がこれを兼ねてよい）

## 3. 課題の3段階

既存の Colab 教材の最大の弱点は、課題がすべて「直前に見たものの書き写し」だったこと。これを構造で防ぐ。

| 段 | 画面に出す名前 | 内部の呼び名 | `kind` | 問題数 | 渡すもの | 判定 |
|---|---|---|---|---|---|---|
| 1 | **例題** | なぞる | `trace` | 1〜2問 | 手順そのもの | 出力の一致 |
| 2 | **練習問題** | 変える | `modify` | 2〜3問 | 動くコード＋変更の指示 | 出力の一致、または隠しテスト |
| 3 | **演習問題** | 組む | `build` | **1〜2問（必須）** | 仕様だけ。コードは渡さない | 隠しテスト（複数の入力） |

**「組む」が0問の節は不合格。** 例外はない。

読むだけのコード例（`<Run>`。▶ を押すと動く）は「**例**」と呼び、課題とは別に扱う。

**内部の呼び名は仕様書とコードの中だけで使う。** 学習者の画面には出さない。「なぞる・変える・組む」は、その問題が学習者に何をさせるものかを書き手が見失わないための名前である。

### 3.1 各段の例（第1部・関数の節を例に）

**なぞる**

> 次のコードを入力して実行してください。
> ```python
> def add(a, b):
>     return a + b
> print(add(3, 5))
> ```

**変える**

> 上の `add` を、引き算をする `sub` に書き換えてください。`sub(10, 4)` が `6` を返すようにします。

**組む**

> 3つの数を受け取り、いちばん大きい数を返す関数 `largest` を書いてください。`max` は使わないでください。
> 判定に使う入力: `(1, 2, 3)` `(5, 5, 2)` `(-3, -1, -2)` `(0, 0, 0)`

「組む」の問題文には、**判定に使う入力を明記する**。隠しテストの存在を隠さない。境界の場合（同じ値が並ぶ、負の数、0）を必ず含める。

### 3.2 前の節を使う

各節の「組む」問題は、**その節より前で学んだものを最低1つ使う**。使わずに解ける問題は、積み上がりを作れていない。

### 3.3 章の終わりの課題

各章の最後に、その章全体を使う課題を1問置く。所要15〜30分。第1部では、例えば次のようなもの。

- 第1章: 3教科の点数から合計と平均を出す
- 第3章: 入力された数が素数かどうかを判定する
- 第5章: リストから条件に合う要素だけを取り出す関数を書く

## 4. 文章の規約

### 4.1 数値の規定

| 項目 | 規定 |
|---|---|
| 1文の長さ | 60字以内 |
| 1段落の文数 | 3文以内 |
| 節の本文（コードと課題を除く） | 400〜800字 |
| 見出し | 節は h2、節内の区切りは h3。h4 以下を使わない |
| 太字 | 1段落に1箇所まで |
| 比喩 | 1節に1つまで。使ったら直後に比喩でない言い換えを置く |
| 感嘆符 | 本文では使わない |

### 4.2 使ってはいけない表現

**煽り・過小評価**

「簡単に」「たった」「〜するだけで」「あっという間に」「驚くほど」「実は」「なんと」「魔法のように」「便利な」「強力な」「パワフルな」「〜してみましょう！」

理由: 読者が詰まったときに、自分が悪いと感じさせる。また、何ができるようになるかを具体的に書く努力を放棄している。

**曖昧化**

「基本的に」「一般的に」「ある意味」「〜的な」「〜のようなもの」

理由: 条件を書かずに逃げている。条件があるなら書く。ないなら断言する。

**読者の知識の仮定**

「ご存知のとおり」「もちろん」「言うまでもなく」

**回収先のない先送り**

「詳しくは省略しますが」「ここでは深入りしません」

先送りしてよいのは、**どの章で回収するかを明記した場合だけ**。

> ここでは数字が逆向きに流れることだけ押さえてください。式は第6部第2章で導きます。

### 4.3 名前があるものは名前で呼ぶ

抽象的な言い換えをしない。これは今回いちばん重視する規約。

| 書かない | 書く |
|---|---|
| 条件を分岐する方法 | if文 |
| 繰り返しの仕組み | for文 |
| 値を保存しておく箱 | 変数（※比喩として1回だけなら可。直後に「変数」と言い直す） |
| データをまとめて扱う考え方 | リスト |
| 処理をまとめたもの | 関数 |
| 学習を効率化する工夫 | （具体名を書く。ミニバッチ、学習率の減衰、など） |

### 4.4 文体

- 敬体（です・ます）で統一する
- 指示は「〜してください」。「〜しましょう」は使わない
- 体言止めを本文で使わない（表と見出しは可）

## 5. 用語

- 新しい用語は `design/spec/glossary.md` に登録する。登録がない語を本文で使ってはいけない
- 初出時に定義を書く。2回目以降は用語集へのリンクにする
- カタカナ語は初出で英語綴りを併記する（例: 変数（variable））
- 画面に出る文字列（エラーメッセージ、ボタンの文字）は**そのまま引用する**。訳したり要約したりしない

---

## 6. よくある間違い

既存の Colab 教材の第6回（壊れたコードを直す回）は、教材として最も良い部分だった。ただし1回にまとめると、エラーに出会う時期（第1回の5分後）と練習する時期（第6回）がずれる。**各節に分散させる。**

### 6.1 書き方

各「よくある間違い」は次の3つを持つ。

1. **壊れたコード**（実際に初学者が書く形）
2. **出るエラーメッセージ**（実際の出力をそのまま。日本語に訳さない）
3. **原因と直し方**（1〜3文）

例:

> ```python
> print(“Python”)
> ```
> ```
> SyntaxError: invalid character '“' (U+201C)
> ```
> 全角のダブルクォートを使っています。`"` は半角で入力してください。日本語入力がオンになっていると全角になります。

### 6.2 拾うべき間違いの型

第1部では最低限これらを扱う。出典は既存 Colab 教材の第6回。

- 綴りの間違い（`prit`、`imput`、`ragne`、`integer`）
- 全角文字（`（`、`”`、`：`、`＝`、`１００`、`，`、`　`）
- 閉じ括弧の不足
- コロンの不足（if、for、while、def）
- インデントの不足・過剰
- 代入 `=` と比較 `==` の取り違え
- `>=` を `=>` と書く
- 変数名の不一致（`score` と `scores`、`height` と `hight`）
- 変数名に空白（`my score`）
- `input()` の結果を数値として計算する
- `print` する関数の返り値が `None` になる
- リストの添字を固定してしまう（`animals[1]` を繰り返す）
- 条件の向きを逆にする（偶数を取りたいのに `% 2 == 1`）

### 6.3 採点との連動

演習の採点が誤答を返すとき、**まずその節の「よくある間違い」に当てはまるかを調べ、当てはまればその説明を出す。** 当てはまらないときだけ、一般的な誤答応答を出す。詳細は `20-platform.md`。

## 7. レベル別の補助

### 7.1 記法

本文中に次の形で置く。レベル0では開いた状態、レベル1では閉じた状態、レベル2では表示しない。

```
:::level0 タイトル
中身
:::
```

### 7.2 書いてよいこと

**操作だけ。**

- どのキーを押すか（「`Shift` を押しながら `2` で `"` が入ります」）
- どこをクリックするか
- 画面のどこに何が出るか
- 日本語入力の切り替え方

### 7.3 書いてはいけないこと

**概念の説明。** 「変数とは何か」をレベル0の補足に書いてはいけない。レベル1の読者も同じだけ知らないからである。概念は全員が読む本文に書く。

## 8. 節のチェックリスト

節を1つ書いたら、これにかける。**1つでも × があればその節は不合格。**

### 構造

- [ ] 最初の要素が「困る例」である。機能の紹介から始まっていない
- [ ] 「困る例」は具体的な場面で、できない状態を書いている
- [ ] 説明より先に、実行できるコードと実行結果が置かれている
- [ ] 新しく名前を付ける概念が1つだけである
- [ ] 「よくある間違い」が1〜3個あり、実際のエラーメッセージが載っている
- [ ] 課題が4〜7問ある
- [ ] 「組む」課題が1問以上ある
- [ ] 「組む」課題に、判定に使う入力が明記されている
- [ ] 「組む」課題が、その節より前の内容を最低1つ使う
- [ ] 「組む」課題の判定に、境界の場合（同値・負・0・空）が含まれている

### 文章

- [ ] すべての文が60字以内である
- [ ] すべての段落が3文以内である
- [ ] 本文が400〜800字である
- [ ] 第4.2節の禁止表現を1つも使っていない
- [ ] 名前があるものを抽象語で言い換えていない（第4.3節）
- [ ] 比喩が1つ以下で、使った場合は直後に言い換えがある
- [ ] 先送りした話題に、回収先の章が明記されている
- [ ] 本文に感嘆符がない
- [ ] 敬体で統一されている

### 用語とレベル

- [ ] 使っている用語がすべて用語集に登録されている
- [ ] 初出のカタカナ語に英語綴りが併記されている
- [ ] エラーメッセージを訳さずそのまま引用している
- [ ] レベル0の補足に概念の説明が入っていない

## 9. レッスンの画面

### 9.1 方針の変更

旧サンドボックスの「1画面固定・スクロール禁止」は、**教材では採用しない。** 本文を読む以上スクロールは避けられない。代わりに守るのは次の1つ。

> **コードを実行するために、読んでいる場所から離れない。**

本や Colab に対する優位はここにある。読む・動かす・直す・答えるを、画面を移動せずに回せること。

### 9.2 構成

```
┌─ 上部 ───────────────────────────────────────┐
│ 章と節の名前 / 進度（この章の何節目か）          │
├─────────────────────────┬───────────────────┤
│                         │                   │
│  本文（最大 720px）      │  右レール 240px    │
│                         │                   │
│  ・文章                  │  ・章内の節の一覧   │
│  ・コード例（その場で実行）│   （済 / いま / 未）│
│  ・図・実験              │  ・用語集への入口   │
│  ・演習（その場で採点）    │  ・先生に聞く      │
│                         │                   │
└─────────────────────────┴───────────────────┘
```

- 本文は1カラム、最大720px
- **コード例はすべてその場で実行できる**（▶ 実行）。別画面に飛ばない
- **演習は編集できるエディタと採点ボタンを本文中に置く**。結果もその場に出る
- 図と実験は本文中に埋め込む。1つの実験は1つのことだけを見せる
- 右レールは章の中の位置を示す。章をまたぐ移動はここからはしない

### 9.3 節の移動

節の終わりに「次の節へ」を置く。前の節へ戻る手段も同じ場所に置く。章の一覧は上部から開く。

### 9.4 引き継ぐ設計原則

`design/PRINCIPLES.md` のうち、教材でも有効なもの:

- **原則4 触れば分かる形にする。** 実験の操作方法は説明文ではなく、触ったときの反応で伝える
- **原則5 原因と結果が1対1で結びつく。** 実験は、1つの操作に1つの見える変化を返す
- **原則6 人の間合いに合わせる。** 採点の結果は操作から700ms以内に返す
- **原則7 読む必要があるものは読める大きさにする。** 本文16px以上、コード14px以上

適用しないもの:

- **原則1（いま触れるものだけ見せる）・原則2（要素を一度に一つ）・原則3（答えを言わない）は教材では使わない。** 教材は説明する場である。ただし**演習の答えは伏せる**。これは原則3の名残ではなく、採点の要請による

## 10. 例・例題・練習問題・演習問題の見分け

### 10.1 狙い

学習者が**文字を読まずに、次に来るものが何かを見分けられる**ようにする。最初のうちは名前を読むが、何節か進めば形と色だけで「これは自分で書く番だ」と分かる。

そのために、4つの種類に**それぞれ違う見た目を割り当てる**。違いは色だけにしない。色が分からない人にも形で伝わるようにする。

### 10.2 割り当ての条件

| 種類 | 学習者がすること | 見た目に求めること |
|---|---|---|
| 例 | 読む。▶ を押すと動く | いちばん軽い。本文の流れを切らない |
| 例題 | 示された通りに打つ | 例より重いが、まだ易しいと分かる |
| 練習問題 | 動くコードを直す | 手を動かす番だと分かる |
| 演習問題 | 仕様だけから書く | **いちばん重い。** ここから自分の頭で考えると分かる |

- 4つは**同じ形の色違いにしない**。枠の有無、角、帯の位置など、形そのものを変える
- 番号を振る（例題1、練習問題2…）。節をまたいで通し番号にはせず、節の中で数える
- 色の意味が分からなくても、**ラベルの文字を読めば必ず分かる**こと

### 10.3 決め方

`public/design-explorations/lesson-picker.html` に候補を並べ、ユーザーが選ぶ。決まったら本節に結果を書く。

### 10.4 教材の見た目の裁量

**レッスンの画面は、サイト本体のデザイントークンに縛られない。**

- マストヘッドとナビはサイト共通のまま
- 本文の中（書体・行間・字間・課題の枠・色・余白）は、**読みやすさを優先して別に組んでよい**
- サイト本体（`design/DECISIONS.md` の第1次デザイントークン）は変えない

理由: 紀要風のトークンは読み物には合うが、コードと課題が混ざる画面では窮屈になる。教材は一日に何十分も見る画面なので、そちらを優先する。
